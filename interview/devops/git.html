Git

1. What's the difference between git merge and git rebase, and when would you choose one over the other?​

📖 Introduction​

This is the single most common Git question in interviews, and the actual answer is about history shape, not just mechanics.

🔀 git merge​

Combines two branches by creating a new merge commit that has two parents — the original branch's history stays exactly as it happened, including every individual commit, and the merge commit records the point where the two histories came back together.

git checkout main
git merge feature-branch

🔁 git rebase​

Replays your branch's commits one by one on top of the target branch's latest commit, producing a linear history with no merge commit at all — as if your changes had been made starting from the target branch's current tip in the first place.

git checkout feature-branch
git rebase main

🎯 When to Choose Each​

Merge preserves the true, exact history of when and how branches actually diverged and came together — genuinely valuable for a shared branch where that history matters. Rebase produces a cleaner, linear history — commonly preferred for tidying up a personal feature branch before it's merged, but genuinely risky on a branch other people are also working from, from the later question in this chapter on rewriting shared history.

💎 Good to Know: This Choice Is About Trade-offs, Not a Universally Correct Answer​

A team's actual convention here varies genuinely reasonably — the important thing in an interview is being able to articulate the trade-off clearly, not asserting one is unconditionally better than the other.

2. What actually happens internally when you run git commit — how does Git store that commit?​

📖 Introduction​

Understanding Git's internal object model turns nearly every other question in this chapter from memorized trivia into something you can actually reason through.

🧩 The Objects Involved​

A blob stores the actual content of a file. A tree represents a directory, listing the blobs and other trees it contains, essentially a snapshot of your project's file structure at that moment. A commit object points to one specific tree, representing the complete state of the project at that commit, along with metadata — author, message, and a pointer to its parent commit, or commits for a merge commit.

🔧 What Happens on git commit​

Git creates a new tree object representing the currently staged content, then creates a new commit object pointing to that tree and to the current commit as its parent, and finally moves the current branch pointer forward to this new commit.

💎 Good to Know: Every Commit Is a Full Snapshot, Not Just a Diff​

A genuinely common misconception is that Git stores commits as diffs, like some other version control systems — internally, a commit points to a complete tree snapshot of the entire project at that moment; Git computes diffs on the fly for display purposes, but that's not how commits are actually stored.

3. What's the difference between git fetch and git pull?​

📖 Introduction​

These two are easy to conflate since both retrieve data from a remote — the difference is in what each one does with it afterward.

📥 git fetch​

Downloads new commits and branch data from a remote repository, updating your local copies of the remote's branches, but doesn't touch your current working branch or its files at all.

git fetch origin

📥 git pull​

Runs git fetch, and then immediately attempts to merge, or rebase depending on configuration, the fetched changes into your current branch.

git pull origin main

🎯 Why This Distinction Matters​

git fetch lets you see what's changed on the remote and decide what to do about it before touching your own working branch — genuinely useful for reviewing incoming changes first. git pull is a convenience combining both steps, but it means a merge, or rebase, is happening automatically, potentially producing an unexpected conflict right when you weren't necessarily prepared to deal with one.

💎 Good to Know: git pull Is Genuinely Just fetch Plus merge (or rebase) Under the Hood​

Knowing this decomposition is itself a common interview follow-up — being able to explain pull as a composition of two more primitive operations, rather than as its own separate, opaque mechanism, is exactly the kind of internals-aware answer this chapter is building toward.

4. What is a merge conflict, and how would you resolve one that touches the same lines in two different branches?​

📖 Introduction​

A merge conflict is Git explicitly telling you it can't safely decide something on your behalf — worth understanding precisely when that happens.

⚠️ What It Is​

When merging or rebasing, if the same lines of the same file were changed differently on both branches, Git can't automatically determine which version is correct, and marks the file as conflicted, leaving both versions visible with conflict markers for you to resolve manually.

<<<<<<< HEAD
const timeout = 5000;
=======
const timeout = 10000;
>>>>>>> feature-branch

🔧 How to Resolve It​

Edit the file to keep the correct, intended final content, removing the conflict markers entirely, then stage the resolved file and complete the merge or rebase.

git add resolved-file.js
git commit

💎 Good to Know: A Conflict Only Happens When the Same Lines Genuinely Diverge — Not Just From Both Branches Touching the Same File​

Two branches can both modify entirely different parts of the same file with no conflict at all — Git only flags a conflict when it genuinely can't determine which of two overlapping changes to the same specific lines should actually win.

5. What's the difference between resetting, reverting, and checking out a previous commit?​

📖 Introduction​

These three all involve "going back" to a previous state, but they do genuinely different things to your history.

⏪ git reset​

Moves the current branch pointer to a different commit, from the later question in this chapter on its three modes — this rewrites history, since the branch now points somewhere else entirely, as if the commits after that point never happened on this branch.

↩️ git revert​

Creates a brand-new commit that undoes the changes of a specific previous commit, without altering any existing history at all — the original commit still exists, and a new one on top of it cancels out its effect.

git revert abc1234

👀 git checkout (a Specific Commit)​

Moves your working directory to look at a specific commit's content, without moving any branch pointer at all — genuinely just for looking, and leaves you in a detached HEAD state, from the later question in this chapter.

💎 Good to Know: revert Is the Safe Choice for Already-Shared History, reset Is Not​

This distinction directly sets up the later question in this chapter about undoing an already-pushed commit — revert adds new history everyone can safely receive; reset removes history that others may have already built on top of, which is exactly why it's risky on a shared branch.

6. What's the difference between git reset --soft, --mixed, and --hard?​

📖 Introduction​

git reset has three distinct modes, each affecting a different amount of your repository's state.

🟢 --soft​

Moves the branch pointer, but leaves your staged changes and working directory files untouched — everything from the "undone" commits is still staged, ready to be recommitted differently.

🟡 --mixed (the Default)​

Moves the branch pointer and unstages the changes, but leaves the actual file contents in your working directory unchanged — you'd need to git add again before committing.

🔴 --hard​

Moves the branch pointer and discards both the staged changes and any actual file modifications in your working directory entirely — genuinely destructive if those changes weren't saved anywhere else.

git reset --soft HEAD~1
git reset --hard HEAD~1

💎 Good to Know: --hard Is the One Genuinely Risky Mode Worth Double-Checking Before Running​

--soft and --mixed are both safely recoverable, since your actual file content is preserved either staged or in the working directory — --hard is the one mode that can genuinely, permanently discard uncommitted work if you haven't verified you actually want to lose it.

7. What is a detached HEAD state, and how do you get out of it safely?​

📖 Introduction​

This is a genuinely common source of confusion for developers newer to Git's internals.

🧩 What It Is​

Normally, HEAD points to a branch, which in turn points to a commit. In a detached HEAD state, HEAD points directly to a specific commit instead of to a branch — this happens after checking out a specific commit directly, from earlier in this chapter, rather than a branch name.

⚠️ Why It's Worth Being Careful About​

Any new commits made while in this state aren't attached to any branch at all — if you switch to a different branch afterward without first creating a new branch to hold them, those commits can become unreachable and eventually be garbage collected.

🔧 How to Get Out Safely​

If you want to keep any new work made in this state, create a new branch pointing to your current commit before switching away.

git checkout -b new-branch-name

💎 Good to Know: Git Genuinely Warns You About This the Moment You Enter a Detached HEAD State​

Checking out a specific commit directly prints an explicit warning about exactly this risk — worth actually reading that message rather than dismissing it, since it's telling you precisely what this question covers.

8. What is interactive rebase (git rebase -i), and what's a realistic use case for it?​

📖 Introduction​

Interactive rebase extends the basic rebase mechanic from the first question of this chapter with genuine, fine-grained control over history.

🔧 What It Is​

Lets you review and modify a series of commits before they're replayed — reordering them, combining several into one (squashing), editing individual commit messages, or dropping specific commits entirely.

git rebase -i HEAD~4

This opens an editor listing the last four commits, letting you mark each one as pick, squash, reword, or drop.

🎯 A Realistic Use Case​

Cleaning up a feature branch's messy, incremental commit history — several small "fix typo" or "address review comment" commits — squashing them together into fewer, more meaningful commits before merging, so the resulting history is easier for teammates to actually read later.

💎 Good to Know: This Should Only Be Done on Commits That Haven't Been Shared Yet​

Interactive rebase rewrites commit history exactly like a regular rebase, from the first question of this chapter — doing it on commits other people have already pulled and built on top of causes the same shared-history problems covered in the later question in this chapter on undoing pushed commits.

9. What's the difference between git stash and committing work-in-progress to a branch?​

📖 Introduction​

Both let you set aside unfinished work temporarily — the difference is in intent and permanence.

📦 git stash​

Temporarily saves your uncommitted changes, staged and unstaged, and reverts your working directory to a clean state, letting you switch branches or pull in changes without those changes getting in the way — genuinely meant to be reapplied shortly after.

git stash
git stash pop

💾 Committing Work-in-Progress​

Creates an actual, permanent commit, even if the work is genuinely incomplete — visible in history, pushable to a remote, and not something you're expected to "pop" back off shortly after.

🎯 When to Use Each​

A stash fits a brief, immediate interruption — you need to quickly switch context and come right back. A WIP commit fits genuinely pausing work for longer, especially if you want that in-progress state backed up somewhere beyond your own local machine.

💎 Good to Know: A Stash Is Easy to Forget About and Lose Track Of​

Since a stash isn't part of your normal, visible commit history, it's genuinely easy to accumulate several forgotten stashes over time — git stash list is worth checking periodically if you use stashing frequently.

10. What branching strategy would you use for a team shipping to production frequently, and why?​

📖 Introduction​

This applied question connects Git workflow directly to the deployment-frequency reasoning covered in the Production Scenario Questions guide.

🎯 A Reasonable Strategy​

A trunk-based approach — short-lived feature branches merged frequently into a single main branch, kept in a genuinely always-deployable state, rather than long-lived branches that diverge significantly before eventually merging.

🎯 Why This Fits Frequent Shipping​

The Production Scenario Questions guide's Deployment & DevOps Scenarios chapter covers exactly why smaller, more frequent deploys reduce risk — a branching strategy with short-lived branches and frequent, small merges directly supports that same goal, since large, infrequently merged branches tend to produce larger, riskier merges and deploys.

💎 Good to Know: The Branching Strategy and the Deployment Strategy Are Genuinely Connected Decisions​

This is a direct, practical link between two guides in this repo — how a team branches in Git and how frequently and safely it can actually deploy aren't independent choices; a long-lived-branch workflow tends to work against exactly the frequent, low-risk deployment cadence covered in the Production Scenario Questions guide.

11. What's the difference between a fast-forward merge and a three-way merge?​

📖 Introduction​

Not every merge actually needs a merge commit — this question is about when Git can take a shortcut.

⏩ Fast-Forward Merge​

When the branch being merged in is simply ahead of the current branch, with no divergent commits on the current branch at all, Git can just move the current branch's pointer forward to match — no new merge commit is created at all, since there's nothing genuinely to reconcile.

🔀 Three-Way Merge​

When both branches have diverged, each with their own distinct commits since they split, Git creates a genuine merge commit, from the first question of this chapter, combining both histories, using the common ancestor commit as the reference point for merging.

💎 Good to Know: --no-ff Forces a Merge Commit Even When a Fast-Forward Would Otherwise Be Possible​

Some teams deliberately use git merge --no-ff to always create an explicit merge commit, even for a fast-forward-eligible merge, specifically to preserve a visible record in history that a feature branch existed and was merged, rather than having it silently disappear into a fast-forwarded main branch.

12. How would you find which commit introduced a specific bug using git bisect?​

📖 Introduction​

This is a genuinely practical, often underused tool for exactly the kind of "which recent change caused this" investigation covered generally in the Production Scenario Questions guide.

🔧 How It Works​

You tell Git a known-bad commit, current, and a known-good commit, some point in the past before the bug existed — Git then checks out a commit roughly halfway between the two, and you test and tell it whether that commit is good or bad, repeating this binary search until Git narrows it down to the exact commit that introduced the problem.

git bisect start
git bisect bad
git bisect good v1.2.0

🎯 Why This Is Efficient​

Rather than manually checking out and testing commits one by one in order, bisect's binary search finds the culprit in a logarithmic number of steps — genuinely fast even across a large number of candidate commits.

💎 Good to Know: This Is a Direct, Practical Tool for the "Which Deploy Caused This" Scenario Covered in the Production Scenario Questions Guide​

The Production Scenario Questions guide's Debugging & Production Issues chapter covers investigating a delayed regression generally — git bisect is a genuinely concrete, powerful tool for exactly that investigation when the cause is a specific code change somewhere in a range of commits.

13. What's the difference between .gitignore and removing an already-tracked file from version control?​

📖 Introduction​

This is a genuinely common point of confusion, since .gitignore alone doesn't do what people sometimes assume.

🚫 .gitignore​

A file listing patterns for files and directories Git should never start tracking in the first place — it only affects untracked files; it has no effect at all on a file that's already being tracked.

🗑️ Removing an Already-Tracked File​

If a file was already committed before being added to .gitignore, it remains tracked and continues showing up in commits regardless — you need to explicitly remove it from tracking.

git rm --cached secrets.env

This removes the file from Git's tracking, while .gitignore prevents it from being re-added afterward.

💎 Good to Know: This Is Exactly Why a Secret Accidentally Committed Before Being Added to .gitignore Isn't Actually Fixed by Just Adding It There​

This directly connects to the leaked-credential scenario covered in the Production Scenario Questions guide's Authentication & Security Scenarios chapter — adding a secret to .gitignore after it was already committed does nothing to remove it from history; the credential still needs to be treated as compromised and rotated, exactly as that scenario covers.

14. How would you undo a commit that's already been pushed to a shared branch, without disrupting your teammates?​

📖 Introduction​

This closing question pulls together the reset-versus-revert distinction from earlier in this chapter into the one scenario where the choice genuinely matters most.

⚠️ Why This Is Different From Undoing a Local, Unpushed Commit​

Once a commit is pushed and others may have already pulled it, rewriting history with reset and a force push, from earlier in this chapter, would remove commits your teammates' local repositories still have — causing confusing divergence and requiring everyone to manually reconcile their own history against the rewritten one.

🔧 The Safe Approach​

Use git revert, from earlier in this chapter, instead — it adds a new commit undoing the change, without removing or altering any existing, already-shared history at all, meaning teammates can simply pull the new revert commit normally, exactly like any other new change.

git revert abc1234
git push

💎 Good to Know: This Closing Question Is the Direct, Practical Payoff of the Reset-vs-Revert Distinction From Earlier in This Chapter​

Every earlier question in this chapter about history rewriting — rebase, reset, interactive rebase — carries this same underlying caution once shared, pushed history is involved; revert is consistently the safe tool specifically because it never requires anyone else to reconcile a rewritten history.
