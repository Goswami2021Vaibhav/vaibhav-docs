Docker

1. What is a container, and how does it differ fundamentally from a virtual machine?​

📖 Introduction​

This distinction is the foundation everything else in this chapter builds on.

📦 What a Container Is​

An isolated process, or group of processes, running on the host machine's own operating system kernel, but with its own isolated view of the filesystem, network, and process space — achieved through OS-level isolation features, not a separate, full operating system.

🖥️ How This Differs From a Virtual Machine​

A virtual machine runs an entire separate guest operating system, including its own kernel, on top of virtualized hardware — genuinely heavier, since every VM carries the full weight of a complete OS. A container shares the host's kernel directly, making it dramatically lighter weight, faster to start, and more resource-efficient, at the cost of slightly weaker isolation than a genuinely separate, fully virtualized guest OS provides.

💎 Good to Know: "Shares the Kernel" Is the Single Fact That Explains Nearly Every Container Characteristic​

Container start time measured in milliseconds rather than a VM's typical seconds-to-minutes, and a container's much smaller resource footprint, both trace directly back to this one architectural difference — worth having this as the anchor fact for reasoning through nearly any other container-versus-VM comparison question.

2. What is a Docker image, and how does it relate to a running container?​

📖 Introduction​

This is the class-versus-instance relationship that underlies everything else in this chapter.

📀 What an Image Is​

A read-only template containing everything needed to run an application — the application code, its dependencies, and the filesystem layers, from the next question, that make up its environment — built once from a Dockerfile and then reusable to create containers from repeatedly.

🏃 How It Relates to a Container​

A container is a running instance created from an image — the image itself never changes; Docker adds a thin, writable layer on top of the image's read-only layers specifically for that one running container, letting it make changes without ever modifying the underlying image.

docker build -t my-app .
docker run my-app

💎 Good to Know: You Can Run Many Independent Containers From the Exact Same Image​

Since the image itself is immutable and each container gets its own separate writable layer, from earlier in this chapter, you can start several genuinely independent containers from the same single image, each with its own isolated runtime state, without any of them interfering with each other or with the original image.

3. What are Docker layers, and how does Docker's build cache use them to speed up rebuilds?​

📖 Introduction​

Understanding layers is what makes Dockerfile-writing decisions, like the instruction-ordering question later in this chapter, actually make sense rather than feeling arbitrary.

🧱 What Layers Are​

Each instruction in a Dockerfile, RUN, COPY, ADD, produces a new, distinct layer stacked on top of the previous one — an image is really just an ordered stack of these layers.

⚡ How the Build Cache Uses Them​

When rebuilding an image, Docker checks each instruction in order — if a given instruction and everything before it are unchanged since the last build, Docker reuses the already-built layer from its cache rather than re-executing that instruction, only actually rebuilding from the first genuinely changed instruction onward.

🎯 Why This Matters in Practice​

A rebuild that only changes application code, without touching dependency installation, can skip re-running the potentially slow dependency-install step entirely, if that step is structured as an earlier, unchanged layer — directly setting up the instruction-ordering question later in this chapter.

💎 Good to Know: Layer Caching Is the Entire Reason Dockerfile Instruction Order Is a Genuine Performance Decision, Not Just Style​

Every later question in this chapter about structuring a Dockerfile efficiently traces directly back to this one underlying mechanism — worth treating this as the foundational fact the rest of this chapter's practical advice is built on.

4. What's the difference between the CMD and ENTRYPOINT instructions in a Dockerfile?​

📖 Introduction​

Both specify what actually runs when a container starts — the difference is in how flexible and overridable that is.

▶️ CMD​

Specifies the default command to run, but it can be entirely overridden by whatever command is passed when starting the container.

CMD ["node", "server.js"]
docker run my-app node other-script.js

This replaces the entire CMD with node other-script.js.

🔒 ENTRYPOINT​

Specifies a command that always runs, with any arguments passed at docker run appended to it rather than replacing it entirely.

ENTRYPOINT ["node"]
CMD ["server.js"]

Running the container without arguments runs node server.js; passing an argument at docker run replaces just the CMD portion, still running through the fixed ENTRYPOINT.

💎 Good to Know: Using Both Together Is a Genuinely Common, Deliberate Pattern​

Combining a fixed ENTRYPOINT with a default, overridable CMD, exactly as shown above, gives you a container with a consistent, unchangeable core command while still letting the specific arguments passed to it be easily overridden at run time — worth recognizing this combination as intentional, not redundant.

5. Why does the order of instructions in a Dockerfile matter for build performance?​

📖 Introduction​

This directly applies the layer-caching mechanism from earlier in this chapter to an actual, practical writing decision.

🎯 Why Order Matters​

Since Docker's build cache, from earlier in this chapter, invalidates from the first changed instruction onward, placing instructions that change rarely, installing dependencies, before instructions that change frequently, copying application source code, means a typical rebuild after only a source-code change can reuse the cached dependency-installation layer entirely, rather than re-running it every single time.

COPY package.json package-lock.json ./
RUN npm install
COPY . .

Copying only the dependency manifest first, installing dependencies, and only then copying the rest of the source code means an unchanged package.json lets the npm install layer stay cached even when application code changes.

💎 Good to Know: Getting This Order Wrong Is One of the Most Common, Concrete Docker Performance Mistakes​

A Dockerfile that copies the entire source tree, application code included, before running npm install invalidates the dependency-install cache on literally every single code change, no matter how small — a genuinely common, avoidable mistake that meaningfully slows down every rebuild.

6. What's the difference between a bind mount and a named volume in Docker?​

📖 Introduction​

Both let a container access data outside its own writable layer, from earlier in this chapter — the difference is in where that data actually lives and who manages it.

📁 Bind Mount​

Maps a specific path on the host machine's own filesystem directly into the container — the container sees and can modify the exact same files that exist on the host at that path.

docker run -v /home/user/app:/app my-app

📦 Named Volume​

A storage location managed entirely by Docker itself, not tied to any specific host path you have to know or manage — Docker handles where it actually lives on disk.

docker run -v app-data:/app/data my-app

🎯 When to Use Each​

A bind mount is genuinely useful for local development, letting you edit source code on your host machine and see changes reflected immediately inside a running container. A named volume is generally the better fit for genuinely persistent application data, like a database's files, since it's managed by Docker and isn't tied to a specific, potentially fragile host directory structure.

💎 Good to Know: This Choice Directly Sets Up the Docker Compose Chapter's Data-Persistence Question​

The next chapter of this guide covers persisting a database's data across container restarts using Docker Compose — that's exactly the named-volume use case described here, just configured declaratively rather than via a docker run flag.

7. What is a multi-stage build, and what problem does it solve?​

📖 Introduction​

Multi-stage builds are a direct, deliberate answer to the image-size question later in this chapter.

🏗️ What It Is​

A Dockerfile with multiple FROM instructions, each starting a new, separate build stage — later stages can selectively copy specific files from earlier stages, without carrying over everything else those earlier stages contained.

FROM node:20 AS build
WORKDIR /app
COPY . .
RUN npm install && npm run build

FROM node:20-slim
COPY --from=build /app/dist ./dist
CMD ["node", "dist/server.js"]

🎯 What Problem It Solves​

Without multi-stage builds, a single build stage that installs dev dependencies and build tools to compile or bundle an application would leave all of that build tooling sitting in the final image, unnecessarily bloating it — a multi-stage build lets the final image contain only the actual compiled output, discarding everything the build stage needed but the running application doesn't.

💎 Good to Know: This Is the Primary, Concrete Technique Behind the Next Question's Image-Size Reduction​

Multi-stage builds are consistently the single biggest lever for reducing a Node.js application's image size, directly answering the next question in this chapter — build tooling and dev dependencies are genuinely large and genuinely unnecessary in the image that actually runs in production.

8. How would you reduce the size of a Docker image for a Node.js application?​

📖 Introduction​

This applied question pulls together several techniques from earlier in this chapter into one concrete, practical answer.

🔧 Techniques​

Use a multi-stage build, from the previous question, so the final image only contains the built application and its production dependencies, not build tooling or dev dependencies. Use a smaller base image variant, like a -slim or -alpine tagged Node.js image, rather than the full, default image, which includes many tools genuinely unneeded at runtime. Use a .dockerignore file to prevent unnecessary files, node_modules from the host, git history, local config, from ever being copied into the image's build context at all. Install only production dependencies in the final stage, using npm install --omit=dev or equivalent, rather than including development-only packages.

💎 Good to Know: A Smaller Image Isn't Just About Disk Space — It Also Means Faster Deploys and a Smaller Attack Surface​

A smaller image pulls and deploys faster, and contains fewer installed packages that could carry a vulnerability, from the Web Security guide's Dependency & Supply Chain Security chapter — image size is a genuine, multi-dimensional concern, not purely a storage-cost optimization.

9. What's the difference between exposing a port with EXPOSE and actually publishing it with -p?​

📖 Introduction​

This is a genuinely common point of confusion for anyone newer to Docker networking.

📢 EXPOSE (in the Dockerfile)​

Purely documentation and metadata — it declares which port the containerized application listens on, but doesn't actually make that port reachable from outside the container's own internal network on its own.

EXPOSE 3000

🔌 -p (at docker run)​

Actually publishes a port, mapping a port on the host machine to a port inside the container, making the containerized application genuinely reachable from outside.

docker run -p 8080:3000 my-app

🎯 Why This Distinction Matters​

A container can be perfectly healthy and correctly listening on its EXPOSEd port internally, yet be completely unreachable from the host machine or the outside world if it was never actually published with -p — a genuinely common cause of "my container is running but I can't reach it" confusion.

💎 Good to Know: EXPOSE Is Informational Even Between Containers on the Same Docker Network​

Containers on the same user-defined Docker network, covered in the next question, can actually reach each other's ports directly without needing -p at all — -p specifically matters for reaching a container from outside Docker's own network entirely, from the host machine or the wider internet.

10. How does Docker networking let containers communicate with each other by default?​

📖 Introduction​

This directly follows up on the note at the end of the previous question.

🌐 How It Works​

Containers connected to the same user-defined Docker network can reach each other directly, by container name, over that internal network — Docker provides automatic DNS resolution, so one container can simply address another by its name rather than needing to know its actual internal IP address.

docker network create my-network
docker run --network my-network --name api my-api-image
docker run --network my-network --name db my-db-image

The api container can reach the db container simply by connecting to the hostname db.

🎯 Why This Matters in Practice​

This is exactly the mechanism the next chapter's Docker Compose setup relies on for services to communicate with each other — Compose automatically creates this kind of shared network for you, letting service names double as reachable hostnames.

💎 Good to Know: The Default Bridge Network Doesn't Provide This Automatic DNS Resolution — a User-Defined Network Does​

Containers started without specifying a network land on Docker's default bridge network, which doesn't support this convenient name-based resolution — this is exactly why creating an explicit, user-defined network, or using Docker Compose, from the next chapter, which does this automatically, is the practical, recommended approach.

11. What happens to data inside a container when the container is removed, and how would you prevent losing it?​

📖 Introduction​

This directly connects back to the image-versus-container relationship covered earlier in this chapter.

💥 What Happens​

A container's writable layer, from the earlier image-versus-container question in this chapter, is deleted along with the container itself when it's removed — any data written only to that writable layer, and not stored in a volume, is genuinely, permanently lost.

🔧 How to Prevent This​

Store any data that needs to survive beyond the container's own lifetime in a named volume, or a bind mount, both from earlier in this chapter, rather than relying on the container's own writable layer — a database's data directory being a genuinely common, concrete example of exactly this need.

docker run -v db-data:/var/lib/postgresql/data my-db-image

💎 Good to Know: This Is Precisely Why a Database Running in a Plain, Volume-less Container Is a Common, Costly Mistake​

Running a database container without an attached volume, and later removing or recreating that container for any reason, whether intentional or accidental, permanently loses all of its data — a genuinely serious, avoidable mistake that this chapter's volume guidance directly exists to prevent.

12. How would you debug a container that's crashing immediately after it starts?​

📖 Introduction​

This closing question turns every concept covered in this chapter into an actual diagnostic process.

🔍 Diagnostic Approach​

Check the container's logs first — the actual error message or stack trace the crashing process produced is almost always the fastest, most direct way to understand what went wrong.

docker logs <container-id>

Check whether the issue is actually the CMD/ENTRYPOINT, from earlier in this chapter, itself — running the image interactively with a shell instead of its normal command lets you poke around and manually verify the environment is actually set up the way the application expects.

docker run -it my-app /bin/sh

Confirm any required environment variables, covered in the next chapter of this guide, or mounted volumes, from earlier in this chapter, that the application depends on at startup are actually present and correctly configured.

💎 Good to Know: A Container That "Crashes Immediately" Almost Always Has an Informative Log Message Waiting — Check It First​

The single most common mistake in this exact debugging scenario is skipping straight to guessing or poking around before actually reading docker logs — the crashing process's own error output is nearly always the fastest path to the actual root cause.
