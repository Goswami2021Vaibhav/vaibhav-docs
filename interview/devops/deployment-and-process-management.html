Deployment & Process Management

1. What is a reverse proxy, and why does a Node.js application commonly sit behind one like Nginx in production?​

📖 Introduction​

This closing chapter is about the last mile — actually getting a built, tested application running reliably and safely in front of real users.

🔀 What a Reverse Proxy Is​

A server that sits in front of one or more backend application servers, receiving incoming client requests and forwarding them to the appropriate backend — the same reverse-proxy concept covered generally in the Networking guide's Firewalls, Proxies, VPNs & NAT chapter.

🎯 Why a Node.js App Commonly Sits Behind One​

A reverse proxy like Nginx handles concerns a Node.js application shouldn't have to handle directly — TLS termination, from later in this chapter, serving static files efficiently, from later in this chapter, and load balancing, from the Scalability guide, across multiple running instances, from later in this chapter — letting the Node.js process itself focus purely on application logic.

💎 Good to Know: This Is the Concrete, Practical Application of a Concept Already Covered Generally Elsewhere in This Repo​

The Networking guide covers reverse proxies as a general networking concept; this chapter is specifically about the practical, everyday reasons a real Node.js deployment actually reaches for one.

2. What does Nginx do beyond simply forwarding requests to your application?​

📖 Introduction​

"Forwarding requests" undersells what a reverse proxy actually does in a typical, real deployment.

🎯 What Else It Does​

TLS termination, from later in this chapter, decrypting HTTPS traffic before it reaches the application. Serving static files, from later in this chapter, directly, far more efficiently than routing every single static asset request through the Node.js process. Load balancing, from later in this chapter, distributing traffic across multiple running application instances. Basic request filtering and rate limiting at the network edge, before a request ever reaches the application at all.

server {
  listen 443 ssl;
  location /api/ {
    proxy_pass http://localhost:5000;
  }
  location / {
    root /var/www/frontend;
  }
}

💎 Good to Know: Nginx Is Doing Real, Substantial Work Here — Not Just Passively Sitting in the Middle​

Each of these responsibilities is genuinely handled more efficiently by Nginx, a purpose-built tool for exactly this, than by adding the equivalent logic into the Node.js application itself — worth thinking of Nginx as doing real, substantial infrastructure work, not merely relaying traffic passively.

3. What is a process manager like PM2, and what problem does it solve that just running node app.js doesn't?​

📖 Introduction​

Running a Node.js application directly in a terminal is fine for local development — production needs something more robust.

🔧 What It Is​

A tool that runs and supervises a Node.js application as a managed, background process — restarting it automatically if it crashes, from the next question, managing multiple instances, from later in this chapter, and providing logging and monitoring around the running process.

pm2 start app.js --name my-api

⚠️ The Problem With Just node app.js​

If the process crashes, from an unhandled exception or any other reason, it simply stops — nothing brings it back automatically, and if it was running in a terminal session that closes, the application stops along with it.

💎 Good to Know: A Process Manager Is Genuinely Necessary Infrastructure, Not an Optional Convenience​

Running an application this simply in production, with no supervision at all, means a single unhandled error takes the entire application down until someone manually notices and restarts it — a process manager exists specifically to remove that entirely avoidable risk.

4. How does a process manager automatically restart a crashed application, and why does that matter in production?​

📖 Introduction​

This directly answers the mechanism referenced in the previous question.

🔄 How It Works​

The process manager runs as its own separate, supervising process, watching the application process it started — if that application process exits unexpectedly, the process manager immediately starts a new instance of it.

🎯 Why This Matters in Production​

A single unhandled exception, from this repo's Node.js guide's error-handling chapter, or an unexpected crash shouldn't mean an application stays down until a human notices and manually restarts it — automatic restart keeps downtime to the brief moment it takes the process manager to actually detect the crash and start a new instance, rather than an indefinite outage.

💎 Good to Know: Automatic Restart Is a Safety Net, Not a Substitute for Fixing the Actual Underlying Bug​

A process that keeps crashing and automatically restarting in a loop is still a genuine, unresolved problem — this mirrors the same caution covered in the Production Scenario Questions guide's API & Backend Scenarios chapter, where a restart loop quietly masks an underlying issue rather than actually resolving it.

5. What is zero-downtime deployment, and how would you achieve it for a Node.js application?​

📖 Introduction​

This directly applies the general zero-downtime deployment principle covered in the Production Scenario Questions guide's Deployment & DevOps Scenarios chapter to Node.js specifically.

🎯 What It Is​

Deploying a new version of an application without any window where the application is completely unavailable to serve requests — covered generally in that Production Scenario Questions guide chapter's closing question.

🔧 How to Achieve It for Node.js​

Run multiple instances, from the next question, and use the process manager's own reload capability, which starts new instances running the updated code and only shifts traffic to them, from Nginx's load balancing role, from earlier in this chapter, once they're confirmed ready, terminating the old instances only after that handoff completes.

pm2 reload my-api

💎 Good to Know: This Is the Concrete, Node.js-Specific Implementation of a Principle Already Covered Generally in This Repo​

The Production Scenario Questions guide's closing zero-downtime question covers the general "old and new versions briefly coexist correctly" principle — this question is exactly that principle, implemented concretely using a process manager's reload capability and Nginx's traffic routing.

6. How would you run multiple instances of a Node.js application on the same server to use multiple CPU cores?​

📖 Introduction​

This connects directly to Node.js's own single-threaded execution model, covered in this repo's Node.js guide.

⚠️ The Underlying Constraint​

A single Node.js process runs its JavaScript on one thread, from this repo's Node.js guide's event-loop chapter — a single process can't, on its own, use more than one CPU core for handling requests, no matter how many cores the server actually has available.

🔧 How to Use Multiple Cores​

Run multiple separate Node.js process instances, one per available CPU core, with a process manager, from earlier in this chapter, managing all of them, and a reverse proxy, from earlier in this chapter, load balancing incoming requests across them.

pm2 start app.js -i max

💎 Good to Know: This Is Horizontal Scaling Applied Within a Single Machine, Not Just Across Multiple Servers​

This is the same underlying horizontal-scaling principle covered generally in the Scalability guide, just applied at the scope of one single server's multiple cores rather than multiple separate machines — running more independent instances, rather than making one instance somehow use more than one thread.

7. What's the difference between a reverse proxy handling TLS termination and the application handling it directly?​

📖 Introduction​

This directly extends the Networking guide's SSL/TLS chapter into a practical deployment-architecture decision.

🔐 Reverse Proxy Handling TLS Termination​

The reverse proxy, from earlier in this chapter, handles the TLS handshake, from the Networking guide's SSL/TLS chapter, decrypting incoming HTTPS traffic and forwarding the request to the application over plain, unencrypted HTTP internally, typically over a trusted, private network the application and proxy share.

🔐 The Application Handling TLS Directly​

The Node.js application itself manages certificates and performs the TLS handshake directly, with no reverse proxy involved in that specific responsibility at all.

🎯 Why TLS Termination at the Proxy Is the More Common Choice​

Nginx is a purpose-built, highly optimized tool for exactly this, from earlier in this chapter's coverage of what Nginx does beyond forwarding — centralizing certificate management at the proxy layer also means the application itself doesn't need to be concerned with TLS configuration at all, keeping that responsibility cleanly separated.

💎 Good to Know: Internal Traffic Between Proxy and Application Is Typically Still Within a Trusted, Private Network Boundary​

Traffic between the reverse proxy and the application, while technically unencrypted after termination, typically never leaves a trusted, private network boundary — the actual public-facing, untrusted-network leg of the journey, from the Networking guide, is exactly the part that remains genuinely encrypted end to end.

8. How would you configure Nginx to serve static frontend assets while proxying API requests to a backend?​

📖 Introduction​

This applied question combines two of Nginx's responsibilities, from earlier in this chapter, into one common, real configuration.

🔧 Configuration​

server {
  listen 80;

  location /api/ {
    proxy_pass http://localhost:5000;
  }

  location / {
    root /var/www/frontend/build;
    try_files $uri /index.html;
  }
}

Requests to /api/ are forwarded to the running Node.js backend; every other request is served directly from the frontend's built static files, with try_files falling back to index.html to support a client-side-routed single-page application, from this repo's React guide.

🎯 Why This Split Matters​

Static assets are served directly by Nginx, far more efficiently than routing them through the Node.js process, from earlier in this chapter, while dynamic API requests still reach the actual application — a genuinely common, practical MERN deployment shape.

💎 Good to Know: try_files Falling Back to index.html Is Specifically for Client-Side Routing​

Without this fallback, directly navigating to a client-side route, refreshing the page on /dashboard, for instance, would return a 404 from Nginx, since no actual file exists at that path — falling back to index.html lets the frontend's own router, from this repo's React guide, take over and render the correct view client-side instead.

9. What logs would you actually want to check first if a deployed application isn't responding?​

📖 Introduction​

This applied, diagnostic question pulls together every layer covered throughout this chapter into one practical investigative sequence.

🔍 Where to Look​

The reverse proxy's own logs, from earlier in this chapter, first — confirming whether requests are even reaching Nginx at all, and if so, what response it's actually getting back from the application, or whether it's failing to reach the application entirely. The process manager's logs, from earlier in this chapter, next — checking whether the application process is actually running, or has crashed and is stuck in a restart loop, from earlier in this chapter's caution about that exact scenario. The application's own logs last — the actual error or stack trace, if the process is running but genuinely misbehaving rather than being down entirely.

💎 Good to Know: This Sequence Moves From the Outermost Layer Inward, Isolating Where the Failure Actually Is​

Checking the reverse proxy first, then the process manager, then the application itself mirrors the same layer-isolation diagnostic approach covered throughout the Production Scenario Questions guide — narrowing down which specific layer is actually failing before assuming where the problem lives.

10. How would you design a deployment process that takes a fresh git push all the way to a live, running application?​

📖 Introduction​

This closing question, and this final chapter, pulls together every concept covered across this entire DevOps guide into one complete, end-to-end deployment pipeline — and closes out this entire project's full scope of subjects.

🔧 The Full Pipeline​

A git push, from the Git chapter of this guide, triggers a CI/CD pipeline, from the CI/CD chapter of this guide, which builds and tests the application, producing a versioned, reusable artifact, from that same chapter — a Docker image, from the Docker chapter of this guide. Once tests pass, the pipeline deploys that exact artifact, injecting environment-specific configuration, from the Environment & Configuration Management chapter of this guide, at deploy time rather than baking it into the image. The process manager, from earlier in this chapter, starts the new version's instances, using a zero-downtime reload, from earlier in this chapter, so old and new versions briefly coexist correctly rather than any window of unavailability. Nginx, from earlier in this chapter, sits in front of the whole deployment, terminating TLS, serving static assets, and load balancing across the running instances, from earlier in this chapter.

💎 Good to Know: This Closing Design Is Genuinely the Sum of Every Chapter in This Guide, and a Fitting Close to This Entire Project​

Git for version control and safe collaboration, Docker for a consistent, portable build, Docker Compose for local development that mirrors that same shape, environment and configuration management for safe, per-environment values, CI/CD for automated, confidence-building testing and artifact reuse, and this chapter's process management and reverse proxy for actually running it all reliably — every one of this repo's interview-prep guides, from Web Security through this final DevOps chapter, has been building toward exactly this same underlying goal: genuinely understanding not just how to write an application, but how to take it all the way to real, production users safely and reliably.
