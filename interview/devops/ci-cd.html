CI/CD

1. What's the difference between continuous integration and continuous deployment?​

📖 Introduction​

These two terms, and the "CI/CD" acronym itself, are commonly used together but refer to genuinely separate practices.

🔀 Continuous Integration (CI)​

The practice of frequently merging code changes into a shared branch, with each merge automatically triggering a build and test run — the goal is catching integration problems and bugs quickly, close to when they were actually introduced, rather than letting them accumulate.

🚀 Continuous Deployment (CD)​

The practice of automatically deploying every change that passes CI straight to production, with no manual step in between — genuinely the more aggressive, fully automated end of the deployment spectrum.

🎯 Why the Distinction Matters​

A team can practice CI, automatically building and testing every change, without practicing continuous deployment at all — deploying manually, or on a schedule, instead. The two are genuinely separate decisions, not a single, indivisible practice, despite frequently being bundled together under one acronym.

💎 Good to Know: This Chapter Covers the Full Spectrum, Not Just the Fully Automated End​

Continuous delivery, covered later in this chapter, sits genuinely between these two — worth having this chapter's full spectrum in mind rather than treating "CI/CD" as one single, all-or-nothing practice.

2. What typically belongs in a CI pipeline's build stage versus its test stage?​

📖 Introduction​

A real CI pipeline is usually broken into distinct stages, each with a genuinely different purpose.

🏗️ Build Stage​

Compiling or bundling the application, installing dependencies, and, for a containerized application, building the Docker image itself, from the Docker chapter of this guide — confirming the code actually produces a valid, runnable artifact at all.

✅ Test Stage​

Running the actual test suite — unit tests, integration tests — against the built artifact, confirming the code doesn't just build successfully but genuinely behaves correctly.

jobs:
  build:
    steps:
      - run: npm install
      - run: npm run build
  test:
    needs: build
    steps:
      - run: npm test

🎯 Why Separating Them Matters​

A build failure and a test failure are genuinely different signals worth distinguishing clearly — a build failure means the code doesn't even compile or bundle correctly; a test failure means it builds fine but behaves incorrectly, and separating the stages makes it immediately obvious which kind of problem actually occurred.

💎 Good to Know: Keeping the Build Stage Fast Matters, Since Every Later Stage Depends on It Succeeding First​

Since the test stage, and everything after it, only runs once the build stage succeeds, a slow build stage adds delay to every single pipeline run regardless of what happens afterward — worth keeping this specific stage genuinely fast.

3. Why should tests run automatically on every pull request rather than only before a release?​

📖 Introduction​

This is about catching problems as early and as cheaply as possible, a theme covered generally throughout the Production Scenario Questions guide.

🎯 Why Every Pull Request, Not Just Before Release​

Running tests only right before a release means many changes have already accumulated since the tests last ran — if something breaks, it's genuinely harder to pinpoint which of many recent changes actually caused it, directly related to the delayed-regression-tracing difficulty covered in the Production Scenario Questions guide's Performance Optimization Scenarios chapter. Running tests on every pull request catches a problem immediately, tied to one specific, small change, while it's still fresh and genuinely easy to fix.

💎 Good to Know: This Is the Same "Smaller, More Frequent Changes Reduce Risk" Reasoning Covered in the Git Chapter of This Guide​

The Git chapter of this guide covers exactly this same reasoning for branching strategy and deploy frequency — testing on every pull request is the CI-specific application of that same underlying principle: catch problems small and early, rather than large and late.

4. What is a CI pipeline artifact, and how does it get used later in a deployment pipeline?​

📖 Introduction​

An artifact is the actual, tangible output the build stage, from earlier in this chapter, produces.

📦 What It Is​

A built, packaged output of the build stage — a compiled bundle, a Docker image, from the Docker chapter of this guide — stored somewhere the later stages of the pipeline, or an actual deployment, can retrieve and use.

build:
  steps:
    - run: docker build -t my-app:${{ github.sha }} .
    - run: docker push my-app:${{ github.sha }}

🎯 How It Gets Used Later​

The deployment stage doesn't rebuild the application from source again — it pulls the exact same artifact the build stage already produced and tested, ensuring what actually gets deployed is genuinely identical to what was tested, rather than a fresh, separately built copy that could theoretically differ.

💎 Good to Know: Rebuilding for Deployment Instead of Reusing the Tested Artifact Is a Genuine, Concrete Risk​

If deployment triggers a brand-new build from source rather than reusing the artifact that was actually tested, from earlier in this chapter, there's no longer a strict guarantee that what's deployed is identical to what passed testing — a subtle but genuinely real gap worth avoiding by deliberately reusing the same built artifact throughout the entire pipeline.

5. What's the difference between continuous deployment and continuous delivery?​

📖 Introduction​

These two are genuinely easy to conflate, given how similar the terms sound.

🚀 Continuous Deployment​

Every change that passes CI is automatically deployed to production, with no manual step at all, from the first question of this chapter.

📬 Continuous Delivery​

Every change that passes CI is automatically prepared and made ready to deploy — but an explicit, deliberate step, often a manual approval, from the later question in this chapter, is still required before it actually goes live.

🎯 Why the Distinction Matters​

Continuous delivery gives a team the deliberate choice of when exactly to release, while still getting every other benefit of automation — the build, the tests, and the readiness are all automatic; only the final "go live" decision stays a deliberate, human one.

💎 Good to Know: Many Real Teams Practice Continuous Delivery, Not Full Continuous Deployment, and That's a Genuinely Reasonable Choice​

Fully automated continuous deployment to production, with zero human checkpoint at all, is a real, valid practice, but it's not the only legitimate end state — continuous delivery, with a deliberate final approval step, is an equally legitimate, very common choice for teams that want that one specific human checkpoint before production traffic is actually affected.

6. How would you design a pipeline that builds a Docker image and only pushes it to a registry once tests pass?​

📖 Introduction​

This applied question combines the build/test staging from earlier in this chapter with the Docker mechanics covered earlier in this guide.

🔧 Design​

jobs:
  build-and-test:
    steps:
      - run: docker build -t my-app:${{ github.sha }} .
      - run: docker run my-app:${{ github.sha }} npm test
  push:
    needs: build-and-test
    steps:
      - run: docker push my-app:${{ github.sha }}

The image is built once, tests run against that exact built image, and the push to the registry only happens as a genuinely separate, later step, gated on the test step's success.

🎯 Why This Ordering Matters​

This ensures a genuinely broken image, one that fails its own tests, from earlier in this chapter, is never pushed to the registry at all — anything available in the registry for later deployment has already, provably passed the test stage.

💎 Good to Know: This Directly Applies the Artifact Reuse Principle From Earlier in This Chapter​

This design is a concrete instance of the earlier artifact-reuse question in this chapter — the exact same image built once is what's tested and, only if that succeeds, what's pushed and later deployed, rather than any risk of rebuilding a subtly different image at each stage.

7. What is a deployment gate, and what's a realistic reason to require manual approval before a production deploy?​

📖 Introduction​

This directly extends the continuous-delivery concept from earlier in this chapter into a concrete pipeline mechanism.

🚧 What It Is​

An explicit checkpoint in a pipeline that pauses automated progress until a specific condition is met, commonly an explicit, manual approval from a designated person or team, before the pipeline proceeds to its next stage, typically the actual production deployment.

deploy-production:
  needs: deploy-staging
  environment:
    name: production
  # requires manual approval configured on this environment

🎯 A Realistic Reason for One​

Deploying to production during a specific, sensitive business period, a major sales event, for instance, where a team wants a deliberate, human checkpoint confirming it's genuinely the right moment, even though the change itself has already passed every automated check.

💎 Good to Know: A Deployment Gate Doesn't Replace Automated Testing — It Adds a Deliberate, Separate Kind of Check​

A gate isn't a substitute for the automated build and test stages, from earlier in this chapter — it's an additional, deliberate checkpoint for the kind of judgment call automation genuinely can't make, like organizational timing or business risk tolerance.

8. How would you handle a secret, like a deployment credential, needed by a CI/CD pipeline itself?​

📖 Introduction​

This directly extends the Environment & Configuration Management chapter of this guide's secrets guidance to the pipeline's own needs.

🔧 How to Handle It​

Store the credential using the CI/CD platform's own built-in, encrypted secrets storage, rather than embedding it directly in the pipeline configuration file itself, which is typically version-controlled and would otherwise expose it exactly the way the Git chapter of this guide's secrets question warns against.

steps:
  - run: deploy.sh
    env:
      DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}

🎯 Why This Matters​

A pipeline configuration file lives in the same repository as the application code, from the Git chapter of this guide — a credential hardcoded directly into it would be committed to version control exactly like any other secret, carrying the exact same permanent-exposure risk covered throughout the Environment & Configuration Management chapter of this guide.

💎 Good to Know: This Is the Same Secrets-Management Discipline From Earlier in This Guide, Now Applied to the Pipeline's Own Credentials​

The pipeline itself needs credentials to actually deploy — treating those credentials with the exact same care as any other secret covered in the Environment & Configuration Management chapter of this guide is worth being just as deliberate about, since a pipeline's deployment credential is often especially powerful and consequential if ever leaked.

9. What would you do if a CI pipeline passes but the exact same code fails once deployed?​

📖 Introduction​

This directly extends the CI-versus-production gap covered generally in the Production Scenario Questions guide.

🔍 What to Investigate​

Whether CI and production genuinely run under the same conditions — configuration, from the Environment & Configuration Management chapter of this guide, dependency versions, or infrastructure differences between the CI environment and actual production, exactly the differences covered in the Production Scenario Questions guide's Deployment & DevOps Scenarios chapter's CI-versus-production question.

🎯 Why "Exact Same Code" Doesn't Mean "Exact Same Conditions"​

CI typically runs in a controlled, often simplified environment — a passing CI run proves the code is correct under CI's specific conditions, from that Production Scenario Questions guide chapter's framing, not that it's correct under every condition production might actually present.

💎 Good to Know: This Question Is a Direct, Concrete Application of a Scenario Already Fully Covered Elsewhere in This Repo​

Rather than introducing new reasoning, this question is about recognizing and applying the exact investigative approach the Production Scenario Questions guide already covers in depth for precisely this scenario.

10. How would you design a pipeline to support rolling back a bad deploy quickly?​

📖 Introduction​

This closing question connects directly to the fast, practiced rollback capability covered in the Production Scenario Questions guide's Deployment & DevOps Scenarios chapter.

🔧 Design​

Keep every deployed artifact, from earlier in this chapter, tagged and retrievable, so rolling back means simply redeploying a previous, already-built and already-tested artifact, rather than needing to rebuild an older version of the code from scratch under time pressure.

docker pull my-app:previous-known-good-sha
docker run my-app:previous-known-good-sha

Have a genuinely fast, low-friction way to actually trigger this rollback — a single pipeline job or command, rather than a long, manual sequence of steps that adds delay exactly when speed matters most.

🎯 Why This Matters​

This directly delivers the fast-rollback capability the Production Scenario Questions guide identifies as the necessary first response to a bad deploy — a rollback mechanism that's slow or unpracticed defeats the entire purpose of having one, right when a genuine incident makes speed the priority.

💎 Good to Know: This Closing Question Ties the Entire Chapter Together — Reusable Artifacts, Fast Feedback, and a Practiced, Low-Friction Recovery Path​

Every earlier concept in this chapter — build-once-reuse artifacts, from earlier in this chapter, fast feedback from testing every change, from earlier in this chapter — exists specifically to make both shipping confidently and recovering quickly from a mistake genuinely possible, which is exactly the point this closing question makes explicit.
