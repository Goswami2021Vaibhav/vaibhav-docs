Expiration & Eviction

1. What is a TTL in Redis, and how do you set one on a key?​

📖 Introduction​

TTLs were used throughout the Caching Strategies chapter of this guide — this is where they get full, dedicated coverage.

⏰ What It Is​

Time-to-live — an amount of time after which a key is automatically considered expired and removed, without needing anything in your application to explicitly delete it.

🔧 How to Set One​

SET session:abc123 "user-data" EX 3600
EXPIRE session:abc123 3600
TTL session:abc123

EX on SET sets an expiration at the moment of writing the key; EXPIRE sets or updates a TTL on a key that already exists; TTL checks how much time remains.

💎 Good to Know: A Key Without an Explicitly Set TTL Lives Forever by Default​

Unless a TTL is deliberately set, a key persists indefinitely — this is exactly why the earlier Caching Strategies chapter's warning about forgetting to set a TTL at all is a genuinely common, real mistake, not a hypothetical one.

2. What happens to a key once its TTL expires — is it removed instantly, or does Redis check for it lazily?​

📖 Introduction​

Expiration doesn't happen through one single, unified mechanism — Redis actually combines two different approaches.

🔄 Two Removal Mechanisms​

Lazy expiration — Redis checks a key's TTL when that key is actually accessed, and if it's expired, removes it right then, before returning a result, rather than treating it as still present. Active expiration — Redis also periodically, in the background, samples a portion of keys with a TTL set and proactively removes any that have already expired, even if nothing has actually requested them recently.

🎯 Why Both Exist Together​

Lazy expiration alone would let expired keys that are never actually accessed again sit around indefinitely, still consuming memory; active expiration alone, running continuously and exhaustively, would add unnecessary overhead. Combining both gets accessed keys correctly expired immediately on access, while the background process gradually cleans up ones that aren't being accessed at all.

💎 Good to Know: There's a Small, Normal Window Where an Expired Key May Still Technically Exist in Memory​

Because active expiration only samples a portion of keys periodically rather than checking every key continuously, an expired key that isn't accessed can briefly continue existing in memory until the background sweep gets to it — this is expected, normal behavior, not a bug.

3. What is a Redis eviction policy, and why does it only matter once memory is under pressure?​

📖 Introduction​

Eviction is a genuinely different mechanism from expiration, from the previous two questions, even though both result in a key disappearing.

🧩 What It Is​

A configured policy that decides which keys Redis should remove when the instance is at its configured maximum memory limit and needs to free up space to accept new writes.

🎯 Why It Only Matters Under Memory Pressure​

Eviction is specifically a response to memory being full — a Redis instance with plenty of memory headroom never needs to evict anything at all, regardless of which policy is configured; the policy only actually gets exercised once the configured memory limit is genuinely reached.

💎 Good to Know: Eviction Removes Keys That Haven't Necessarily Expired at All​

This is a key distinction from expiration, from earlier in this chapter — eviction can remove a key that has no TTL, or one whose TTL hasn't come close to expiring yet, purely because memory is under pressure and the configured policy selected it for removal.

4. What's the difference between the allkeys-lru and volatile-lru eviction policies?​

📖 Introduction​

Both use the same LRU logic, from the next question — the difference is in which keys are actually eligible to be evicted at all.

🌐 allkeys-lru​

Considers every key in the database eligible for eviction under memory pressure, from earlier in this chapter, regardless of whether it has a TTL set or not.

🎯 volatile-lru​

Only considers keys that actually have a TTL set as eligible for eviction — keys with no expiration set are never evicted under this policy, even under severe memory pressure.

🤔 Why This Distinction Matters​

volatile-lru lets you deliberately protect certain keys from ever being evicted, simply by not giving them a TTL, while still allowing genuinely cache-like, expiring data to be evicted as needed — allkeys-lru makes no such distinction and treats the entire keyspace as fair game.

💎 Good to Know: This Choice Directly Reflects Whether Redis Is Being Used Purely as a Cache or for a Mix of Data​

This connects directly to the cache-versus-primary-store distinction from the Introduction & Fundamentals chapter of this guide — volatile-lru fits a Redis instance holding a genuine mix of disposable cache data and important, non-expiring data; allkeys-lru fits an instance used purely and entirely as a cache.

5. What does LRU actually mean, and how does Redis approximate it rather than tracking exact usage recency?​

📖 Introduction​

LRU is the most common eviction strategy, and Redis's specific implementation is a deliberate, practical approximation.

🧩 What It Means​

Least Recently Used — when eviction needs to happen, remove whichever key hasn't been accessed for the longest time, on the theory that data that hasn't been touched in a while is the least likely to be needed again soon.

🎯 How Redis Approximates It​

Tracking the exact, precise access time of every single key would itself add real memory and computation overhead. Instead, Redis samples a small, random subset of keys and evicts the least recently used one among just that sample — a good-enough approximation of true LRU that avoids the overhead of tracking every single key's exact access history.

💎 Good to Know: This Approximation Is a Deliberate Trade-off, Not a Shortcut Taken Reluctantly​

This is the same underlying philosophy as HyperLogLog's approximate cardinality, from the Data Types chapter of this guide — a small, controlled amount of imprecision in exchange for meaningfully lower overhead, which is a genuinely good trade for eviction, where getting the exact least-recently-used key isn't actually critical.

6. What is the noeviction policy, and what happens to write commands once memory is full under it?​

📖 Introduction​

noeviction is the deliberately conservative option among the available eviction policies.

🚫 What It Is​

A policy where Redis doesn't evict any keys at all when memory is full — instead of freeing up space, it simply refuses new writes.

⚠️ What Happens to Write Commands​

Once memory is genuinely full under noeviction, write commands start returning an error instead of being accepted — reads continue to work normally against existing data, but the dataset can't grow any further until memory pressure is relieved some other way.

🎯 When This Is the Right Choice​

When losing any data, even data that seems like a good eviction candidate, is genuinely unacceptable — an explicit, loud failure on write is preferable to Redis silently discarding data you actually needed.

💎 Good to Know: noeviction Turns a Memory Problem Into an Application-Visible Error Rather Than Silent Data Loss​

This is a deliberate trade-off — an application using noeviction needs to actually handle and respond to write failures under memory pressure, rather than assuming writes will always quietly succeed the way they would under an eviction-based policy.

7. How would you choose the right eviction policy for a given Redis use case?​

📖 Introduction​

This question asks you to apply the previous questions' distinctions to an actual decision.

🎯 How to Decide​

If Redis is used purely as a cache, where every key is disposable and losing any of it is acceptable, allkeys-lru, from earlier in this chapter, is a reasonable, simple default. If Redis holds a genuine mix of disposable cache data and non-expiring data that must never be evicted, volatile-lru, from earlier in this chapter, lets you protect the latter simply by not setting a TTL on it. If Redis is being used as something closer to a primary store, from the Introduction & Fundamentals chapter of this guide, where losing any data silently is genuinely unacceptable, noeviction, from the previous question, forces an explicit, visible failure instead.

💎 Good to Know: The Right Policy Follows Directly From How the Data Is Actually Being Used, Not a Universal Best Practice​

There's no single "correct" eviction policy in the abstract — the right choice is a direct consequence of the cache-versus-primary-store decision covered throughout this guide, made concrete for this specific instance's actual configuration.

8. What's the difference between a key that has no TTL at all and one whose TTL just hasn't expired yet?​

📖 Introduction​

These two states look identical from a simple GET — the key is present either way — but they behave very differently under memory pressure.

🆚 The Difference​

A key with no TTL at all persists indefinitely and, depending on the eviction policy, from earlier in this chapter, may or may not even be eligible for eviction. A key with a TTL that hasn't expired yet will eventually be automatically removed once that TTL is reached, from earlier in this chapter, and remains eligible for early eviction under memory pressure regardless of policy, since it does have a TTL set.

🔍 How to Check Which State a Key Is Actually In​

TTL some-key

Returns the remaining time in seconds if a TTL is set, -1 if the key exists but has no TTL at all, and -2 if the key doesn't exist.

💎 Good to Know: -1 and -2 Are Genuinely Easy to Confuse, and the Distinction Matters​

Treating "no TTL set" the same as "key doesn't exist" is a real, easy mistake in application code checking TTL's return value — the two states mean genuinely different things and deserve genuinely different handling.

9. Why might you deliberately want some keys to never expire while others do, within the same Redis instance?​

📖 Introduction​

This directly extends the cache-versus-primary-store reasoning from the Introduction & Fundamentals chapter of this guide into a concrete TTL decision.

🎯 Why the Split Makes Sense​

Cache-like data — a cached database query result, from the Caching Strategies chapter of this guide — genuinely benefits from expiring, since it's disposable and should eventually refresh from its source anyway. Other data Redis holds as its own genuine source of truth — a distributed lock's state, or a rate limiter's counter, both covered later in this guide — either needs a TTL tied to its own specific, meaningful lifetime, or in some cases genuinely shouldn't expire at all.

💎 Good to Know: This Is the Same Per-Key, Not Per-Instance, Decision Flagged in the Introduction & Fundamentals Chapter​

The Introduction & Fundamentals chapter of this guide flagged that the cache-versus-primary-store decision is made per key, not once for the whole instance — TTL configuration is the concrete, practical mechanism that actually implements that per-key decision in practice.

10. How would you diagnose unexpected key evictions happening in production?​

📖 Introduction​

This closing question turns every concept from this chapter into an actual investigative process.

🔍 Diagnostic Approach​

Check the instance's current memory usage relative to its configured maximum, since eviction, from earlier in this chapter, only happens once that limit is genuinely being reached — confirm memory pressure is actually the underlying cause before looking anywhere else. Check the currently configured eviction policy, from earlier in this chapter, to understand which keys were actually eligible to be evicted in the first place — an unexpectedly evicted key with no TTL under allkeys-lru behaves very differently than the same situation under volatile-lru. Investigate what's actually driving the memory growth — an unexpectedly large or growing dataset, or keys that were expected to have a TTL but don't, from earlier in this chapter.

💎 Good to Know: Unexpected Eviction Is Almost Always a Symptom of a Deeper Memory or Configuration Issue, Not a Standalone Bug​

Eviction itself is working exactly as configured — the actual investigation should be aimed at why memory pressure is occurring in the first place, or whether the configured policy genuinely matches what the application actually needs, rather than treating the eviction itself as the root problem.
