Replication & High Availability

1. How does primary-replica replication work in Redis?​

📖 Introduction​

This chapter shifts from a single Redis instance to a deployment built for genuine resilience.

🔁 How It Works​

A replica connects to a primary, receives an initial copy of the primary's entire dataset, and then continuously receives a stream of the primary's subsequent write commands, applying each one to keep its own copy up to date — the same conceptual pattern as replica sets covered in this repo's MongoDB guide, with the primary accepting all writes and replicas maintaining their own synchronized copy.

REPLICAOF primary-host 6379

🎯 Why This Matters​

A replica holds essentially the same data as the primary, meaning if the primary becomes unavailable, a replica already has a nearly complete, up-to-date copy ready to potentially take over — the foundation the rest of this chapter builds on.

💎 Good to Know: A Replica Can Also Serve Read Traffic​

Beyond redundancy, a replica can serve read queries directly, spreading read load across more than just the primary — the same read-scaling benefit covered generally for replica sets in this repo's MongoDB guide.

2. What's the difference between synchronous and asynchronous replication, and which does Redis use by default?​

📖 Introduction​

This distinction directly shapes the replication-lag question later in this chapter.

🔄 Synchronous Replication​

The primary waits for a replica to confirm it has received and applied a write before considering that write complete and acknowledging it to the client.

⚡ Asynchronous Replication​

The primary acknowledges a write to the client immediately, without waiting for any replica to confirm it's received that write yet — replication happens in the background, slightly after the fact.

🎯 Which Redis Uses by Default​

Redis replication is asynchronous by default — the primary doesn't wait for replicas to catch up before confirming a write, which keeps write latency low but means a replica can genuinely lag slightly behind the primary at any given moment.

💎 Good to Know: This Default Trades a Small Amount of Consistency Risk for Meaningfully Lower Write Latency​

This is a deliberate design choice consistent with Redis's broader performance-first philosophy, from the Performance & Architecture chapter of this guide — waiting for every replica to confirm every write would add real latency to every single write, in exchange for a stronger consistency guarantee most use cases don't strictly require.

3. What is replication lag, and why can a replica briefly serve stale data?​

📖 Introduction​

This is the direct, practical consequence of the asynchronous default covered in the previous question.

⏱️ What It Is​

The delay between a write being applied on the primary and that same write actually being applied on a given replica — since replication is asynchronous, from the previous question, this delay is never exactly zero, even under normal, healthy conditions.

🎯 Why a Replica Can Serve Stale Data​

If a client reads from a replica, from the previous question's read-scaling benefit, during that small window before a recent write has actually propagated to it, it gets the value as it existed just before that write — genuinely stale, if only briefly.

💎 Good to Know: This Is the Same Replication-Lag Concept Covered Generally in This Repo's MongoDB and Production Scenario Questions Guides​

Replication lag isn't unique to Redis — it's covered generally for MongoDB's replica sets in this repo's MongoDB guide, and as a broader production concern in the Production Scenario Questions guide's Database Scenarios chapter — the underlying cause and trade-off are the same wherever asynchronous replication is used.

4. What is Redis Sentinel, and what problem does it solve that plain replication alone doesn't?​

📖 Introduction​

Replication alone, from earlier in this chapter, gives you redundant copies of the data — it doesn't, by itself, actually do anything about a failed primary.

🚨 The Gap Plain Replication Leaves​

If a primary goes down, plain replication doesn't automatically promote a replica to take over — without something actively monitoring and responding to that failure, the deployment would simply stay without a working primary until someone manually intervenes.

🛡️ What Sentinel Does​

A separate system of Sentinel processes that continuously monitors the primary and its replicas, and when it detects the primary has genuinely failed, from the next question, automatically promotes one of the replicas to become the new primary and reconfigures the rest of the deployment to follow it — turning plain replication's redundancy into genuine, automatic high availability.

💎 Good to Know: Sentinel Is Conceptually Similar to the Automatic Failover Covered in This Repo's MongoDB Guide​

The role Sentinel plays here is genuinely similar to how a MongoDB replica set holds an election to choose a new primary automatically, covered in this repo's MongoDB guide — different underlying mechanism, same fundamental purpose: turning passive redundancy into active, automatic recovery.

5. How does Sentinel detect that a primary has failed, and what does it do next?​

📖 Introduction​

This covers the actual mechanics behind the automatic response introduced in the previous question.

🔍 How It Detects Failure​

Sentinel processes continuously ping the primary and its replicas — if a Sentinel stops receiving a timely response from the primary, it marks it as subjectively down from its own point of view, and checks with the other Sentinels monitoring the same deployment to see whether they agree, using the quorum concept from the next question.

🔄 What Happens Next​

Once enough Sentinels agree the primary is genuinely, objectively down, they coordinate an election among themselves to select which replica should be promoted, then instruct that replica to become the new primary and reconfigure the remaining replicas to follow it instead of the old one.

💎 Good to Know: This Is a Coordinated, Multi-Sentinel Decision, Not a Single Process Acting Alone​

Requiring multiple independent Sentinels to agree before acting is a deliberate safeguard — a single Sentinel's own, possibly incorrect, view that the primary is down isn't enough on its own to trigger a failover, directly setting up the quorum concept covered in the next question.

6. What is quorum in the context of Sentinel, and why does it matter for avoiding a false failover?​

📖 Introduction​

Quorum is the specific safeguard referenced at the end of the previous question.

🧮 What It Is​

The minimum number of Sentinel processes that must agree the primary is genuinely down before a failover is actually triggered.

🎯 Why It Matters​

A single Sentinel might lose connectivity to the primary due to its own network issue, a problem specific to that one Sentinel rather than the primary genuinely being down — without requiring agreement from multiple Sentinels, that one Sentinel's mistaken view alone could trigger an entirely unnecessary failover, disrupting a perfectly healthy primary.

💎 Good to Know: This Is a Consensus Mechanism, the Same General Idea Covered Generally in the Scalability Guide​

Requiring several independent observers to agree before taking a significant, disruptive action is the same underlying consensus principle covered generally in the Scalability guide's distributed systems chapter — Sentinel's quorum is a concrete, specific application of that broader idea.

7. What happens to clients connected to the old primary during a Sentinel-driven failover?​

📖 Introduction​

This question is about the actual, practical experience from the application's side during the moment of transition.

⚠️ During the Failover​

Clients still connected to the old primary will start experiencing errors or timeouts, since it's no longer accepting writes as the deployment's primary, or may already be unreachable if it's genuinely down. There's a brief window, similar to the failover gap covered generally in this repo's MongoDB guide, where the deployment isn't accepting new writes until the newly promoted replica is actually ready.

🔧 How Clients Recover​

A properly configured client, often working alongside Sentinel itself, discovers the new primary's address, either by asking Sentinel directly or through the client library's own Sentinel-aware connection logic, and reconnects to it, resuming normal operation once that new connection is established.

💎 Good to Know: Application Code Needs to Be Sentinel-Aware, Not Just Pointed at a Fixed Primary Address​

An application connecting directly to a hardcoded primary address, with no Sentinel awareness at all, won't automatically recover after a failover — properly handling this requires either a Sentinel-aware client library or the application's own logic for discovering the current primary, rather than assuming the address never changes.

8. What data can be lost during a failover, and why?​

📖 Introduction​

Failover provides genuine resilience, but it isn't a lossless guarantee — this question is about being precise about that.

⚠️ What Can Be Lost​

Any writes that were acknowledged by the old primary but hadn't yet been replicated to the promoted replica at the moment of failure — a direct consequence of asynchronous replication, from earlier in this chapter, where the primary doesn't wait for replicas to confirm a write before acknowledging it to the client.

🎯 Why This Happens​

Since the newly promoted replica only has whatever data it had actually received and applied up to that point, from the replication-lag question earlier in this chapter, any write still "in flight" toward it when the old primary failed is genuinely gone — the new primary has no record of it at all.

💎 Good to Know: This Is a Direct, Concrete Consequence of the Same Trade-off Introduced Earlier in This Chapter​

This is exactly the practical cost of Redis's asynchronous-by-default replication, from earlier in this chapter — high availability through Sentinel doesn't eliminate this risk, it specifically handles the "who becomes the new primary" problem, not the separate "was every write actually replicated in time" problem.

9. How would you design a highly available Redis deployment for an application that can't tolerate much downtime?​

📖 Introduction​

This applied question pulls together every concept covered so far in this chapter into one concrete deployment design.

🔧 Design​

A primary with at least one, ideally more than one, replica, from earlier in this chapter, so there's always a reasonably up-to-date copy of the data ready to take over. A Sentinel quorum, from earlier in this chapter, of at least three Sentinel processes, deployed across genuinely independent failure domains, so a single Sentinel's own connectivity issue can't trigger an incorrect failover or fail to detect a genuine one. Client libraries and application code that are Sentinel-aware, from the earlier question in this chapter, so they can automatically discover and reconnect to the new primary after a failover, rather than requiring manual intervention.

💎 Good to Know: This Design Combines Every Piece Covered in This Chapter So Far Into One Coherent Whole​

Replication for redundancy, Sentinel for automatic detection and failover, quorum for avoiding false positives, and Sentinel-aware clients for actually recovering — this closing-style question tests whether all four pieces are understood as parts of one coherent system, not in isolation.

10. What are the limitations of Sentinel compared to Redis Cluster's built-in high availability, covered next in this guide?​

📖 Introduction​

This closing question previews the next chapter's subject by identifying exactly what Sentinel doesn't solve.

⚠️ What Sentinel Doesn't Solve​

Sentinel provides high availability, from earlier in this chapter, but every replica in a Sentinel-managed deployment still holds the entire dataset — it does nothing to help if the dataset itself has grown too large for a single node to hold, or if write throughput has outgrown what one primary can handle.

🔀 What Redis Cluster Adds​

Redis Cluster, covered in depth in the next chapter of this guide, distributes the data itself across multiple nodes, addressing capacity and write-throughput limits that replication and Sentinel alone can't — while also providing its own built-in high-availability mechanism, conceptually similar to what Sentinel provides but integrated directly into the cluster itself.

💎 Good to Know: Sentinel Solves Availability, Cluster Solves Availability and Scale Together​

This is directly analogous to the replication-versus-sharding distinction covered in this repo's MongoDB guide — Sentinel-managed replication gives you availability without addressing scale; Redis Cluster, covered next, gives you both together, at the cost of meaningfully more operational complexity.
