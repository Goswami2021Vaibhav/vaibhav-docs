Data Types

1. What are the core Redis data types, and what's a realistic use case for each?​

📖 Introduction​

This chapter is the direct, full follow-through of the "data structure server" framing from the Introduction & Fundamentals chapter of this guide.

🧩 The Core Types​

String — a simple value, but also usable as a counter or for bitwise operations, from later in this chapter. Hash — a set of field-value pairs, good for representing an object. List — an ordered sequence of values, good for a queue or a feed. Set — an unordered collection of unique values, good for membership checks. Sorted Set — a set where each member has a score, good for rankings and leaderboards, from later in this chapter. Stream — an append-only log of entries, good for event data, from later in this chapter.

💎 Good to Know: Choosing the Right Type Is Choosing the Right Set of Operations, Not Just a Storage Shape​

The real value in picking the correct data type isn't just "does the data fit this shape" — it's "does Redis provide the exact atomic operations this use case actually needs," a theme that runs through every question in this chapter.

2. What is a Redis String, and beyond simple key-value storage, what are some less obvious things you can do with it?​

📖 Introduction​

The String is Redis's simplest type, but it's genuinely more capable than "store some text."

📝 Basic Usage​

SET user:1:name "Priya"
GET user:1:name

🔢 Less Obvious Uses​

Atomic counters, using INCR and DECR, which increment or decrement a numeric string value in a single, atomic operation — a natural fit for view counts or rate limiting, covered later in this guide. Bitwise operations, using commands like SETBIT and GETBIT, which treat a string as a raw sequence of bits — the foundation of the Bitmap use case covered later in this chapter.

💎 Good to Know: INCR Being Atomic Is What Makes It Genuinely Useful, Not Just Convenient​

Because INCR is a single atomic operation, from the Transactions chapter of this guide's discussion of atomicity, two concurrent requests incrementing the same counter can never race and produce a lost update the way a naive read-then-write-back approach in application code could.

3. What is a Redis Hash, and when would you model data as a hash instead of several separate string keys?​

📖 Introduction​

A Hash is the natural fit for anything that looks like a single object with several fields.

🧩 What It Is​

A single key that maps to a set of field-value pairs — conceptually like a small, embedded object.

HSET user:1 name "Priya" email "priya@example.com" age "29"
HGET user:1 name

🎯 When to Use a Hash Instead of Separate Keys​

When several related fields naturally belong to the same logical entity, a user or a session — storing them as one hash keeps them logically grouped, lets you fetch or update the whole group in one operation, and avoids needing to manage many separate top-level keys that all conceptually belong together.

💎 Good to Know: A Hash Lets You Update One Field Without Touching the Rest​

HSET on a single field only changes that field — the rest of the hash's fields are untouched, similar in spirit to MongoDB's targeted update operators covered in this repo's MongoDB guide, rather than needing to read the whole object, change one field, and write it all back.

4. What is a Redis List, and what's a realistic use case that takes advantage of its ordering?​

📖 Introduction​

A List is specifically about order — that's the property every use case for it actually leans on.

📋 What It Is​

An ordered sequence of values, supporting fast insertion and removal from either end.

LPUSH recent-orders order:501
RPOP recent-orders

🎯 A Realistic Use Case​

A simple task queue — workers pop items off one end with RPOP or LPOP while producers push new items onto the other end with LPUSH, giving a straightforward first-in-first-out processing order. Another common use is a capped "recent activity" feed, where new items are pushed onto one end and the list is periodically trimmed to a fixed length.

💎 Good to Know: A List Is a Reasonable, Lightweight Queue — Streams Are the More Purpose-Built Option​

A List makes a genuinely fine simple queue, but for use cases needing consumer groups, message acknowledgment, or replaying past entries, Streams, covered later in this chapter, are the more purpose-built Redis data type for that job.

5. What is a Redis Set, and what operations make it genuinely useful beyond just storing unique values?​

📖 Introduction​

Uniqueness alone is useful, but a Set's real power shows up in its set-algebra operations.

🧩 What It Is​

An unordered collection of unique values, supporting fast membership checks.

SADD user:1:tags "admin" "verified"
SISMEMBER user:1:tags "admin"

🔢 Operations Beyond Basic Membership​

SINTER to find the intersection between two sets, SUNION to combine them, and SDIFF to find what's in one but not the other — genuinely useful for things like finding users who belong to two specific groups at once, or friends two users have in common.

💎 Good to Know: These Set-Algebra Operations Run Entirely Inside Redis, Without Pulling Data Into Your Application First​

Computing an intersection or union directly in Redis, rather than fetching both sets into application code and computing it there yourself, avoids transferring potentially large amounts of data over the network just to do a computation Redis is already built to do natively and quickly.

6. What is a Redis Sorted Set, and how does the score let it support use cases a plain Set can't?​

📖 Introduction​

Adding a score to each member is the one change that unlocks an entirely different category of use case.

🧩 What It Is​

Like a Set, from the previous question, but every member also has an associated numeric score, and Redis automatically keeps members ordered by that score.

ZADD leaderboard 1500 "player1"
ZADD leaderboard 2200 "player2"

🎯 What This Enables That a Plain Set Can't​

Retrieving members in ranked order, ZRANGE, finding a specific member's rank, ZRANK, or getting everyone within a score range, ZRANGEBYSCORE — none of which a plain Set, with no inherent ordering at all, could support directly.

💎 Good to Know: The Score Doesn't Have to Represent a "Score" in the Gaming Sense​

The score is just a sortable number — it's genuinely common to use it to represent a timestamp, a priority, or any other value you'd want a collection automatically ordered by, not only literal game points.

7. What's a realistic use case for a Sorted Set, like a leaderboard, and how would you actually implement it?​

📖 Introduction​

This applied question turns the previous question's mechanics into a concrete, working design.

🏆 A Leaderboard Implementation​

Each time a player's score changes, ZADD sets their new score against their player ID as the member — Redis automatically keeps the sorted set ordered. To display the top 10 players, ZREVRANGE leaderboard 0 9 WITHSCORES retrieves the highest 10 scores directly, already sorted, without your application needing to sort anything itself.

ZADD leaderboard 2200 "player2"
ZREVRANGE leaderboard 0 9 WITHSCORES

🎯 Why a Sorted Set Fits This So Well​

Getting a player's current rank, ZRANK, and finding everyone near a specific player's score, both come essentially for free from the same underlying structure, without needing a separate query or any application-side sorting logic.

💎 Good to Know: This Same Pattern Extends to Any "Ranked, Frequently Updated List" Problem​

Trending content ranked by recent engagement, a priority queue ordered by urgency, or a "most active users this week" list are all genuinely the same underlying Sorted Set pattern as a leaderboard, just with a different meaning attached to the score.

8. What are Redis Streams, and how do they differ from a List in terms of what they're actually built for?​

📖 Introduction​

Streams were flagged as a more purpose-built option in the earlier List question of this chapter — this is where they get full coverage.

📊 What They Are​

An append-only log of entries, each automatically assigned a unique, ordered ID, designed specifically for event and message data rather than general-purpose list storage.

XADD orders * orderId "501" status "created"
XRANGE orders - +

🆚 How They Differ From a List​

A List, from earlier in this chapter, is a general-purpose ordered sequence — pop an item, and it's gone. A Stream is specifically built around consumer groups, letting multiple consumers each track their own independent position and re-read or replay entries, and around message acknowledgment, letting a consumer confirm it actually processed an entry rather than just removing it blindly.

💎 Good to Know: Streams Are Redis's Answer to "I Need Something More Like a Proper Message Log"​

For a genuine event log or message-queue-like use case, where replay, multiple independent consumers, and acknowledgment actually matter, Streams are the deliberately purpose-built Redis data type — reaching for a List instead means reimplementing a rougher version of what Streams already provide.

9. What is a Bitmap in Redis, and what kind of problem is it genuinely well suited for?​

📖 Introduction​

A Bitmap isn't a separate data type — it's a specific, deliberate way of using the String type's bitwise operations, from earlier in this chapter.

🧩 What It Is​

A String value used as a raw sequence of individual bits, each one addressable and settable independently.

SETBIT user:1:daily-visits 5 1
GETBIT user:1:daily-visits 5
BITCOUNT user:1:daily-visits

🎯 What It's Well Suited For​

Tracking a large number of simple, binary yes/no states extremely compactly — whether a specific user was active on each of the last 365 days, for example, where each day is represented by a single bit rather than a much larger, separate record.

💎 Good to Know: A Bitmap's Real Advantage Is Memory Efficiency at Large Scale​

The genuine benefit here is how little memory is needed — millions of simple binary flags fit into a comparatively tiny amount of space, which is exactly the kind of use case where a more conventional data structure would be significantly less memory-efficient for the same information.

10. What is HyperLogLog, and what tradeoff does it make to estimate cardinality with very little memory?​

📖 Introduction​

HyperLogLog solves "how many unique things" without paying the memory cost of actually tracking every single one of them.

🧩 What It Is​

A probabilistic data structure for estimating the number of unique elements added to it — cardinality — using a small, fixed amount of memory regardless of how many elements are actually added.

PFADD unique-visitors "user1" "user2" "user1"
PFCOUNT unique-visitors

⚖️ The Tradeoff​

Unlike a Set, from earlier in this chapter, which tracks every distinct member exactly and can tell you precisely who's in it, HyperLogLog only gives you an approximate count, with a small, known margin of error — in exchange, its memory usage stays essentially constant even as the number of unique elements grows into the millions, where an actual Set would keep growing in size right along with it.

💎 Good to Know: HyperLogLog Trades Exactness for a Fixed, Predictable Memory Footprint​

The right call specifically for "roughly how many unique visitors did we have today" — where an approximate answer is genuinely fine — but the wrong tool if you actually need to know exactly who those unique visitors were, which is exactly what a Set, from earlier in this chapter, is for instead.

11. How would you choose the right Redis data type for a genuinely new feature you're building?​

📖 Introduction​

This closing question pulls together every type covered in this chapter into one practical decision process.

🔍 What to Ask​

Does the data represent a single object with several fields? A Hash, from earlier in this chapter. Does order matter, and do you need to process items from one or both ends? A List. Do you only care about unique membership, with no ordering or scoring involved? A Set. Do you need members ranked or ordered by some numeric value? A Sorted Set. Is this genuinely event or message data that might need multiple independent consumers or replay? A Stream. Do you just need a fast, atomic counter, or raw bit-level flags at scale? A String, used as a counter or Bitmap.

💎 Good to Know: The Right Answer Comes From the Actual Operations You Need, Not Just the Shape of the Data​

Just as with MongoDB's data modeling, from this repo's MongoDB guide, the deciding factor here is genuinely how the data will be accessed and operated on — not merely what shape it superficially looks like at rest.
