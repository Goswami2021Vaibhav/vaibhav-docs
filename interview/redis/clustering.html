Clustering

1. What problem does Redis Cluster solve that replication alone doesn't?​

📖 Introduction​

This chapter directly follows through on the previous chapter's closing preview.

⚠️ What Replication Alone Doesn't Solve​

Every replica in a plain replication setup, from the previous chapter, holds a full copy of the entire dataset — this gives you redundancy and read scaling, but a single primary is still the one place all writes go, and the entire dataset still has to fit in a single node's memory.

🔀 What Redis Cluster Solves​

Distributes the dataset itself across multiple nodes, so no single node needs to hold the entire dataset or handle the entire write load alone — the same fundamental capacity-and-throughput problem sharding solves generally, covered in this repo's MongoDB guide.

💎 Good to Know: This Is the Redis-Specific Instance of the Same Distinction Covered for MongoDB​

Redis Cluster and MongoDB's sharding, from this repo's MongoDB guide, solve the exact same underlying problem for their respective databases — the concepts in this entire chapter will feel familiar if you've already worked through that guide's Replication & Sharding chapter.

2. What is a hash slot, and how does Redis Cluster use it to decide which node holds a given key?​

📖 Introduction​

Hash slots are the specific mechanism Redis Cluster uses to divide up the keyspace.

🧩 What It Is​

Redis Cluster divides the entire keyspace into 16,384 fixed hash slots. Every key is deterministically mapped to exactly one of these slots based on a hash of the key itself, and each node in the cluster is responsible for owning a specific range of those slots.

CLUSTER KEYSLOT user:1

🎯 How This Decides Which Node Holds a Key​

Since a key's slot is entirely determined by a hash of the key itself, any client, or the cluster itself, can compute which slot a given key belongs to, and therefore which node currently owns that slot, without needing a separate lookup table mapping individual keys to nodes.

💎 Good to Know: This Is Conceptually Similar to a Shard Key, but the Mechanism Is Built In Rather Than Chosen​

Unlike MongoDB, where you explicitly choose a shard key, from this repo's MongoDB guide, Redis Cluster's slot assignment is automatic and based on the key itself — there's no separate shard key decision to make, though the hash-tags question later in this chapter covers a way to influence which keys land in the same slot.

3. How does Redis Cluster route a client's request to the correct node?​

📖 Introduction​

This covers what actually happens when a client sends a command against a clustered deployment.

🧭 How Routing Works​

A client can connect to any node in the cluster and send a command — if that node owns the slot the command's key maps to, from the previous question, it handles the command directly. If it doesn't own that slot, it responds with a redirect telling the client which node actually does, and a cluster-aware client library then sends the command to that correct node instead.

🎯 Why This Differs From a Traditional Sharded Setup​

Unlike a system with a separate, centralized routing layer sitting in front of every node, from this repo's MongoDB guide's sharded-cluster routing, Redis Cluster pushes routing awareness into the client itself — clients cache which node owns which slots and route directly to the correct one on subsequent requests, minimizing the redirect overhead over time.

💎 Good to Know: This Is Why Using a Cluster-Aware Client Library Matters​

A client library that isn't cluster-aware won't correctly follow these redirects, meaning commands can fail or behave unexpectedly against a clustered deployment — this is a genuinely practical, easy-to-miss requirement when adopting Redis Cluster.

4. What is resharding, and when would a cluster need it?​

📖 Introduction​

A cluster's slot distribution isn't necessarily fixed forever — resharding is how it changes.

🔄 What It Is​

The process of moving hash slots, from earlier in this chapter, and the keys within them, from one node to another, redistributing ownership across the cluster's current set of nodes.

🎯 When a Cluster Would Need It​

When adding a new node to the cluster, which needs to be assigned a share of the existing slots to actually start doing useful work, or when removing a node, whose slots need to be redistributed to the remaining nodes before it can safely leave the cluster.

💎 Good to Know: Resharding Can Happen While the Cluster Continues Serving Traffic​

Redis Cluster is designed to support resharding without requiring the entire cluster to go offline — slots are moved incrementally, letting the cluster continue serving reads and writes throughout the process, similar in spirit to the online, non-blocking migration patterns covered generally in the Production Scenario Questions guide.

5. What are hash tags, and why are they necessary for multi-key operations in a clustered setup?​

📖 Introduction​

This covers a specific, deliberate escape hatch within the otherwise fully automatic hash-slot system.

🏷️ What They Are​

A way to force specific keys to map to the same hash slot, from earlier in this chapter, by including a shared substring wrapped in curly braces within each key's name — only that substring is actually used to compute the hash, rather than the entire key.

user:{1000}:profile
user:{1000}:orders

Both keys here hash based only on 1000, guaranteeing they land in the same slot.

🎯 Why They're Necessary​

A command that operates on multiple keys at once only works correctly in a clustered setup if every one of those keys lives on the same node, from the next question — hash tags are how you deliberately guarantee that for keys you know need to be operated on together.

💎 Good to Know: This Is a Deliberate Trade-off Between Even Distribution and Co-Location​

Forcing related keys into the same slot with a hash tag means they'll always live together on the same node, which is convenient for multi-key operations, but it also means you're giving up some of the automatic, even distribution the plain hashing scheme would otherwise provide for those specific keys.

6. Why can't you reliably run a multi-key command across keys that hash to different slots?​

📖 Introduction​

This directly explains the constraint that makes hash tags, from the previous question, necessary in the first place.

⚠️ The Constraint​

A command that touches multiple keys at once, like computing the intersection of two Sets, from the Data Types chapter of this guide, can only execute if every key it touches lives on the very same node — Redis Cluster doesn't automatically coordinate a multi-key operation across several different nodes on your behalf.

🎯 Why This Limitation Exists​

Coordinating an operation across multiple independent nodes, and doing so atomically, is a genuinely more complex distributed-systems problem — Redis Cluster deliberately avoids taking this on for arbitrary multi-key commands, instead requiring the keys involved to already be co-located, which is exactly what hash tags, from the previous question, let you guarantee deliberately.

💎 Good to Know: This Is a Real, Practical Constraint Worth Designing Around From the Start​

Any application planning to adopt Redis Cluster needs to be deliberate about which keys might ever need to participate in the same multi-key operation, and use hash tags accordingly — discovering this constraint only after an existing multi-key command starts failing in a newly clustered deployment is a common, avoidable pain point.

7. How does Redis Cluster handle a node failure, and how does this build on replication and Sentinel-style concepts from earlier in this guide?​

📖 Introduction​

Redis Cluster doesn't reinvent high availability from scratch — it builds directly on the replication foundation from the previous chapter.

🔧 How It Handles a Node Failure​

Each node in a properly configured cluster has one or more replicas, using the same primary-replica replication covered in the previous chapter of this guide. If a node holding a set of slots fails, the cluster detects this, similar in spirit to Sentinel's failure detection from the previous chapter, and automatically promotes one of that node's replicas to take over ownership of its slots.

🎯 How This Builds on Earlier Concepts​

This is essentially replication and automatic failover, both covered in the previous chapter, applied per shard within the cluster, rather than to a single, whole-dataset primary-replica pair — the same underlying mechanisms, just operating at the level of each individual slot-owning node instead of a single deployment-wide primary.

💎 Good to Know: Redis Cluster Has Its Own Built-In Failure Detection, Distinct From Standalone Sentinel​

Redis Cluster nodes communicate directly with each other to detect failures and coordinate promotion, rather than relying on separate Sentinel processes — a genuinely different implementation from the previous chapter's Sentinel, but solving the same fundamental problem for each shard.

8. What's the difference between vertical scaling a single Redis instance and horizontally scaling with Redis Cluster?​

📖 Introduction​

This question situates clustering within the broader vertical-versus-horizontal scaling framing covered generally in the Scalability guide.

📈 Vertical Scaling​

Giving a single Redis instance more memory and more CPU — simpler to operate, since there's still just one node and none of the multi-key constraints or resharding complexity covered earlier in this chapter, but it eventually runs into a hard ceiling once a single machine's resources are exhausted.

🔀 Horizontal Scaling With Redis Cluster​

Distributing the dataset and load across multiple nodes, from earlier in this chapter — removes that single-machine ceiling, at the cost of the genuine added operational complexity covered throughout this chapter.

💎 Good to Know: This Is the Same General Vertical-vs-Horizontal Trade-off Covered in the Scalability Guide, Now With Redis's Specific Costs Attached​

The Scalability guide covers this trade-off generally — this chapter fills in exactly what "the added complexity of horizontal scaling" concretely looks like for Redis specifically: hash slots, resharding, and multi-key operation constraints.

9. What are the operational trade-offs of adopting Redis Cluster versus a simpler primary-replica setup?​

📖 Introduction​

This closing comparison question pulls together the costs and benefits covered throughout this chapter.

✅ What You Gain​

Genuine horizontal scalability — capacity and write throughput that can grow beyond what a single node, or its replicas, could handle, from earlier in this chapter.

⚠️ What It Costs​

Real operational complexity — resharding, from earlier in this chapter, hash-tag design for multi-key operations, from earlier in this chapter, and cluster-aware client libraries, from earlier in this chapter, are all genuinely more involved than operating a single primary with plain replicas, from the previous chapter.

🎯 The Underlying Trade-off​

This mirrors the same "reach for the more powerful, more complex tool only once the simpler one is genuinely exhausted" reasoning covered generally in the Scalability guide and in this repo's MongoDB guide's sharding-avoidance discussion.

💎 Good to Know: This Trade-off Directly Sets Up the Closing Question of This Chapter​

Understanding what clustering genuinely costs operationally is exactly what makes the final question in this chapter — when it's actually worth it — a real, considered decision rather than an automatic "bigger is always better" assumption.

10. When would you genuinely need Redis Cluster, and when would a single, well-resourced instance be enough?​

📖 Introduction​

This closes the chapter with the same deliberate caution against premature complexity that closed the equivalent sharding chapter in this repo's MongoDB guide.

✅ When Cluster Is Genuinely Needed​

When the dataset itself has grown, or is clearly going to grow, beyond what a single, reasonably resourced node can hold in memory, or when write throughput has genuinely outgrown what a single primary can sustain, even with replication, from the previous chapter, for read scaling.

✅ When a Single Instance, or Simple Replication, Is Enough​

When the dataset comfortably fits in memory on a well-resourced single node, and replication with Sentinel, from the previous chapter, already provides sufficient availability and read scaling — reaching for Cluster's added complexity, from earlier in this chapter, before it's genuinely necessary is taking on real operational cost for no actual benefit yet.

💎 Good to Know: This Closing Caution Mirrors the Same One Made for MongoDB's Sharding​

This is directly analogous to the closing caution in this repo's MongoDB guide's Replication & Sharding chapter — a powerful scaling tool with a real, ongoing operational cost is worth reaching for once genuinely needed, not adopted by default just because a dataset happens to be large or growing.
