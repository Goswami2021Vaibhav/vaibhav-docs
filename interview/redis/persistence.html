Persistence

1. Why does Redis, an in-memory store, need persistence at all?​

📖 Introduction​

This chapter fully answers the durability risk flagged in the Introduction & Fundamentals chapter of this guide.

⚠️ The Underlying Problem​

Data that lives only in RAM, from the Introduction & Fundamentals chapter of this guide, is genuinely lost the moment the Redis process restarts or the server crashes — no disk-backed copy exists to recover from unless persistence is deliberately configured.

🎯 Why This Matters​

For pure cache data, this loss is often acceptable, since it can simply be regenerated from the underlying database, from the Caching Strategies chapter of this guide. But for data Redis holds as its own genuine source of truth — a distributed lock's state or a rate limiter's counters, both covered later in this guide — that same loss is a real, meaningful problem. Persistence exists specifically to give Redis a configurable way to survive a restart without losing its data, closing that gap when it actually matters.

💎 Good to Know: Whether You Need Persistence at All Is Itself a Deliberate, Per-Instance Decision​

A Redis instance used purely for disposable cache data may reasonably run with persistence disabled entirely — persistence isn't a universal requirement, it's a deliberate choice made based on what the data actually is, echoing the cache-versus-primary-store framing from the Introduction & Fundamentals chapter of this guide.

2. What is an RDB snapshot, and how does it capture the dataset at a point in time?​

📖 Introduction​

RDB is the simpler, more compact of Redis's two persistence mechanisms.

📸 What It Is​

A single, compact binary file containing a complete snapshot of the entire dataset as it existed at a specific moment — Redis Database, the name of the file format itself.

🔧 How It Captures a Point in Time​

Redis periodically, based on configured save rules — for example, after a certain number of changes within a certain time window — forks the process and writes the current in-memory dataset out to this snapshot file, without interrupting the main process's ongoing command handling.

💎 Good to Know: An RDB Snapshot Only Reflects Data as of the Moment It Was Taken​

Any write that happens after the most recent snapshot, and before the next one or a restart, is genuinely not captured in that snapshot — this gap is exactly what the trade-off question later in this chapter compares RDB against AOF on.

3. What is AOF (Append Only File), and how does it differ from RDB in what it actually records?​

📖 Introduction​

AOF takes a fundamentally different approach from RDB's periodic, whole-dataset snapshot.

📝 What It Is​

A log that records every write operation Redis executes, in order, appended continuously as those operations happen — rather than a snapshot of the resulting data, it's a record of the actual commands that produced that data.

🆚 How It Differs From RDB​

RDB, from the previous question, captures the dataset's state at specific points in time — everything between snapshots is lost if a crash happens in between. AOF records every write as it happens, meaning far less, potentially close to zero, data is lost in a crash, since the log itself reflects nearly every individual write rather than only periodic full-dataset checkpoints.

💎 Good to Know: Recovering From AOF Means Replaying the Recorded Writes, Not Loading a Snapshot Directly​

Where RDB recovery is a straightforward load of the snapshot file, AOF recovery works by replaying the logged commands in order to reconstruct the dataset — a genuinely different recovery mechanism, with its own performance characteristics for very large logs, from the AOF rewriting question later in this chapter.

4. What are the durability trade-offs between RDB and AOF?​

📖 Introduction​

This question makes the comparison implicit in the previous two questions fully explicit.

📸 RDB's Trade-off​

Compact, fast to load on restart, and lower ongoing overhead during normal operation, but can lose everything written since the last completed snapshot if a crash happens in between.

📝 AOF's Trade-off​

Much better durability, since nearly every write is recorded, but the log file is larger, can take longer to load and replay on restart than loading a single RDB snapshot, and depending on the fsync policy, from the next question, can add a bit more ongoing overhead to each write.

🎯 The Underlying Trade-off​

Better durability, from AOF, generally comes with slightly more overhead and slower recovery; better recovery speed and lower overhead, from RDB, comes with a real risk of losing more recent writes — a genuine, deliberate trade-off, not a case where one option is simply better in every respect.

💎 Good to Know: This Comparison Sets Up Why Using Both Together, From Later in This Chapter, Is a Genuinely Common Choice​

Understanding exactly what each one sacrifices is what makes the later question in this chapter, on combining RDB and AOF, make sense — each compensates for a specific weakness the other has.

5. What does the AOF fsync policy control, and how does it trade off performance against durability?​

📖 Introduction​

Even within AOF, from the previous two questions, there's a further, tunable durability decision.

🔧 What It Controls​

How often Redis actually forces the AOF's recent writes from the operating system's buffer down to physical disk — writing to the log file itself doesn't automatically mean the data is safely on durable storage yet, without an explicit fsync.

⚖️ The Trade-off​

always calls fsync after every single write, offering the strongest durability but adding real overhead to every write. everysec calls fsync once per second, batching that overhead in exchange for accepting the small risk of losing up to about a second's worth of the most recent writes in a crash. no leaves that decision entirely to the operating system's own timing, offering the least durability guarantee but the least overhead.

💎 Good to Know: everysec Is the Common, Practical Default for Good Reason​

everysec is frequently the default and the practical sweet spot for many real applications — meaningfully better durability than no, with substantially less overhead than always, accepting a genuinely small, usually acceptable worst-case data loss window in exchange.

6. Can you use RDB and AOF together, and why would you want to?​

📖 Introduction​

This directly follows through on the trade-off comparison from earlier in this chapter.

✅ Yes, Both Can Run Simultaneously​

Redis can be configured to maintain both an RDB snapshot process and an AOF log at the same time, rather than needing to choose only one.

🎯 Why You'd Want Both​

RDB gives you fast, compact snapshots useful for backups and fast restarts, from earlier in this chapter; AOF gives you the much stronger durability guarantee, from earlier in this chapter, that RDB alone can't provide. Running both means you get AOF's superior durability for the actual restart-recovery path, while still having RDB's compact snapshots available for other purposes, like transferring a copy of the dataset elsewhere.

💎 Good to Know: When Both Are Configured, AOF Is Generally Used for Actual Recovery​

Since AOF captures a more complete, recent history of writes than RDB's periodic snapshots, from earlier in this chapter, Redis generally prefers to recover from AOF when both are present and enabled, precisely because it represents less potential data loss — directly setting up the next question in this chapter.

7. What happens during Redis startup if both an RDB file and an AOF file exist?​

📖 Introduction​

This directly answers the question left open at the end of the previous one.

🔄 What Happens​

If AOF is enabled, Redis uses the AOF file to reconstruct the dataset on startup, rather than the RDB snapshot, since AOF generally represents a more complete, more recent record of the actual writes, from the previous question. The RDB file, in this configuration, still exists and can serve other purposes, like backups, but isn't what's actually used to rebuild the in-memory dataset when both are present.

💎 Good to Know: This Behavior Is a Direct, Practical Consequence of AOF's Better Durability, From Earlier in This Chapter​

This isn't an arbitrary rule — it follows directly from the durability comparison covered earlier in this chapter — since AOF is generally the more complete, more current record of what actually happened, it's the more trustworthy source to rebuild from when both are available.

8. What is AOF rewriting, and why does the append-only file need it over time?​

📖 Introduction​

An always-growing log file has an obvious, practical downside — this question is about how Redis manages that.

📈 The Problem It Solves​

Since AOF, from earlier in this chapter, records every single write operation as it happens, the file keeps growing continuously over the life of a Redis instance, even including many redundant, superseded writes — several INCR calls on the same counter, for instance, are each recorded individually, even though only the final resulting value actually matters for reconstructing the current state.

🔧 What Rewriting Does​

Periodically, Redis compacts the AOF file, generating a new, much smaller file that represents the current dataset using the minimum number of commands needed to recreate it, then replaces the old, larger file with this compacted one.

💎 Good to Know: AOF Rewriting Is a Real, Resource-Intensive Operation Worth Being Aware Of​

This connects directly to the earlier chapter's diagnostic question about a suddenly slow Redis instance, from the Performance & Architecture chapter of this guide — a large AOF rewrite in progress is genuinely one of the concrete things worth checking for when diagnosing an unexpected slowdown.

9. What data loss would you actually expect in a Redis crash under each persistence configuration?​

📖 Introduction​

This question asks you to translate every mechanism covered in this chapter into a concrete, practical answer.

💥 Under No Persistence​

Everything since the last restart is lost — the entire in-memory dataset, from the Introduction & Fundamentals chapter of this guide, with nothing to recover from at all.

💥 Under RDB Only​

Everything written since the last completed snapshot is lost, from earlier in this chapter — potentially a meaningful window depending on how frequently snapshots are configured to run.

💥 Under AOF Only​

Depending on the configured fsync policy, from earlier in this chapter, potentially nothing lost at all under always, up to roughly a second's worth under everysec, or a less predictable amount under no.

💥 Under Both RDB and AOF​

The same expected loss as AOF alone, from earlier in this chapter, since AOF is what's actually used for recovery when both are present, from the earlier question in this chapter.

💎 Good to Know: This Is the Practical, Concrete Payoff of Everything Else Covered in This Chapter​

Being able to state precisely what you'd expect to lose under a given configuration, rather than vaguely gesturing at "some data loss is possible," is exactly the kind of concrete, senior-level answer this entire chapter has been building toward.

10. How would you choose a persistence strategy for a Redis instance being used purely as a cache versus one holding data that must survive a restart?​

📖 Introduction​

This closing question directly applies every mechanism from this chapter to the same cache-versus-primary-store decision introduced in the Introduction & Fundamentals chapter of this guide.

🗄️ For a Pure Cache​

Persistence can reasonably be disabled entirely, or configured lightly with RDB only, from earlier in this chapter — since the data is disposable and regenerable from its underlying source, from the Caching Strategies chapter of this guide, the performance and overhead cost of stronger durability, from earlier in this chapter, isn't worth paying for data you don't actually need to protect.

🔐 For Data That Must Survive a Restart​

AOF, with an appropriately strict fsync policy, from earlier in this chapter, and likely combined with RDB, from earlier in this chapter, for fast restarts and backups — the added overhead is a reasonable, deliberate cost for data Redis is genuinely the sole source of truth for.

💎 Good to Know: This Closing Decision Is the Same One Made Throughout This Entire Chapter, Now Applied End to End​

Every question in this chapter has been building toward exactly this decision — the right persistence configuration follows directly from what the data actually is and how much its loss would genuinely cost, not from a single, universal best-practice default.
