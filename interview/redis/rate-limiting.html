Rate Limiting

1. What is rate limiting, and why is Redis a natural fit for implementing it?​

📖 Introduction​

Rate limiting was already flagged as a genuinely common Redis use case back in the Introduction & Fundamentals chapter of this guide — this chapter covers it fully.

🚦 What It Is​

Restricting how many requests a given client, user, or API key is allowed to make within a given period of time, rejecting or delaying requests beyond that limit — covered generally, from the API design side, in the API Design guide's API Security discussion.

🎯 Why Redis Is a Natural Fit​

A rate limiter fundamentally needs a fast, shared counter that every application server instance can read and update consistently, from the Distributed Locking chapter of this guide's discussion of shared, cross-instance state — Redis's speed, from the Performance & Architecture chapter of this guide, and its atomic counter operations, from the Data Types chapter of this guide, are exactly what this need calls for.

💎 Good to Know: This Chapter Directly Builds on the Data Types Chapter's Atomic Counter Discussion​

INCR's atomicity, covered in the Data Types chapter of this guide, is the foundational building block nearly every rate-limiting approach in this chapter relies on — worth having that chapter's reasoning fresh before continuing.

2. How would you implement a simple fixed-window rate limiter using Redis's INCR and EXPIRE?​

📖 Introduction​

This is the simplest rate-limiting approach, and a natural starting point before this chapter's more refined alternatives.

🔧 Implementation​

async function isAllowed(userId, limit, windowSeconds) {
  const key = `ratelimit:${userId}:${Math.floor(Date.now() / 1000 / windowSeconds)}`;
  const count = await redis.incr(key);
  if (count === 1) await redis.expire(key, windowSeconds);
  return count <= limit;
}

🎯 How It Works​

Each fixed time window, a minute, for instance, gets its own key, incremented atomically, from earlier in this chapter, on every request. Setting the key's expiration only on its first increment ensures the counter automatically resets once that window's time has passed.

💎 Good to Know: This Approach Is Simple but Has a Real Edge-Case Weakness Covered Next​

Fixed-window counting is genuinely easy to reason about and implement, which is exactly why it's a common starting point — but it has a specific, well-known boundary problem covered in the next question.

3. What's the problem with a fixed-window rate limiter at the boundary between two windows?​

📖 Introduction​

This is the well-known weakness the previous question's simple implementation carries.

⚠️ The Problem​

A client could send its full allowed quota of requests right at the very end of one window, and then immediately send another full quota's worth right at the very start of the next window — since each window is counted independently, this lets a client burst up to nearly double the intended limit within a short span of time that straddles the boundary between the two windows.

🎯 Why This Happens​

The fixed-window approach, from the previous question, resets the count based purely on clock time, with no awareness at all of how recently the previous window's requests actually happened relative to now.

💎 Good to Know: This Is a Genuine, Well-Known Limitation, Not a Rare Hypothetical Edge Case​

This boundary-burst behavior is a commonly cited, real weakness of fixed-window rate limiting specifically — it's exactly why the sliding-window approach covered in the next question exists as a more precise alternative.

4. What is a sliding window rate limiter, and how does it avoid the fixed-window boundary problem?​

📖 Introduction​

Sliding window fixes the exact weakness covered in the previous question by tracking actual request timing rather than fixed clock buckets.

🔄 What It Is​

Rather than counting requests within fixed, clock-aligned buckets, a sliding window looks at a continuously moving window of time relative to the current moment — "how many requests happened in the last 60 seconds," recalculated fresh on every single request, rather than "how many happened in this fixed minute."

🔧 A Redis Implementation Using a Sorted Set​

async function isAllowed(userId, limit, windowMs) {
  const key = `ratelimit:${userId}`;
  const now = Date.now();
  await redis.zremrangebyscore(key, 0, now - windowMs);
  const count = await redis.zcard(key);
  if (count < limit) {
    await redis.zadd(key, now, `${now}-${Math.random()}`);
    return true;
  }
  return false;
}

Each request's timestamp is added as a member of a Sorted Set, from the Data Types chapter of this guide, scored by when it happened; old entries outside the current window are trimmed away on each check, and the remaining count reflects requests genuinely within the last full window, however it happens to be positioned in time right now.

💎 Good to Know: This Directly Reuses the Sorted Set Pattern From the Data Types Chapter, Applied to a New Problem​

The Data Types chapter of this guide covered Sorted Sets mainly through the leaderboard example — this is the same underlying structure, score-based ordering and range queries, solving a genuinely different problem here.

5. What is the token bucket algorithm, and how would you implement it using Redis?​

📖 Introduction​

Token bucket is a third, genuinely different approach, one that naturally supports allowing occasional bursts.

🪣 What It Is​

A conceptual bucket holds a maximum number of tokens, refilling at a steady rate over time. Each request consumes one token; a request is only allowed if a token is actually available, and is rejected if the bucket is empty.

🔧 A Redis Implementation​

local tokens = tonumber(redis.call("GET", KEYS[1]) or capacity)
local last = tonumber(redis.call("GET", KEYS[2]) or now)
local refill = math.min(capacity, tokens + (now - last) * rate)
if refill >= 1 then
  redis.call("SET", KEYS[1], refill - 1)
  redis.call("SET", KEYS[2], now)
  return 1
end
return 0

Using a Lua script, from the Performance & Architecture chapter of this guide, keeps the read-refill-check-consume sequence atomic, avoiding a race condition between concurrent requests.

🎯 Why It's Different From Fixed and Sliding Windows​

Token bucket naturally allows a burst of requests up to the bucket's full capacity at once, as long as tokens have accumulated, rather than enforcing a strictly even rate — a genuinely different, often more realistic, behavior for many real-world APIs that can tolerate occasional bursts as long as the average rate stays within bounds.

💎 Good to Know: This Is the Exact Same "Atomic, Multi-Step Logic" Need the Distributed Locking Chapter's Lua Example Addressed​

Reading current state, computing a new value, and conditionally acting on it all needs to happen as one atomic unit here, exactly the same shape of problem the Distributed Locking chapter's ownership-check-and-release Lua script solved — the same tool, applied to a different concrete need.

6. How would you rate limit per-user versus globally across all users, and how does that change your Redis key design?​

📖 Introduction​

This applied question is about a design decision that shows up in every implementation covered so far in this chapter.

🔑 Per-User Rate Limiting​

Include the user's identifier as part of the Redis key itself, from the earlier fixed-window example in this chapter — ratelimit:user123:... — so each user's requests are tracked entirely independently of every other user's.

🌐 Global Rate Limiting​

Use a single, shared key with no user-specific component at all, so every request across every user contributes to, and is checked against, the exact same shared counter.

🎯 Why This Distinction Matters​

A per-user limit protects against one specific abusive or overly aggressive user without affecting anyone else; a global limit protects the overall system's total capacity regardless of who's actually generating the load — many real production systems genuinely need both simultaneously, checked as two independent limits.

💎 Good to Know: Key Design Is the Actual Mechanism That Implements This Decision​

The entire per-user-versus-global decision comes down to nothing more than whether the user's identity is baked into the Redis key or not — a genuinely simple mechanism underneath what sounds like a more complex policy decision.

7. How would you rate limit consistently across multiple application server instances?​

📖 Introduction​

This question directly extends the Distributed Locking chapter's core motivation into rate limiting specifically.

⚠️ The Risk of Getting This Wrong​

If each application server instance tracked its own local, in-memory request count, from the Distributed Locking chapter's opening question about why in-process coordination doesn't work across processes, a client's true total request rate, spread across several different instances behind a load balancer, would never be accurately reflected by any single instance's own local count.

🔧 How to Solve It​

Use Redis as the single, shared counter every instance reads from and writes to, exactly as every implementation throughout this chapter has already been doing — since all instances check and increment the same centralized Redis key, the limit is correctly enforced against the client's true total rate, not just whatever fraction happened to land on one specific instance.

💎 Good to Know: This Is the Exact Same Shared-State Requirement Covered for the Rate Limiter Question in This Repo's Production Scenario Questions Guide​

The Production Scenario Questions guide's System Design Scenarios chapter poses exactly this same rate-limiter design question generally — this chapter's answer is the concrete, Redis-specific implementation of the shared-store solution that question is pointing toward.

8. What are the performance considerations of running a rate limiter check on every single incoming request?​

📖 Introduction​

A rate limiter that's meant to protect performance shouldn't itself become a performance problem.

🎯 What to Consider​

Every request now pays the cost of at least one round trip to Redis before it can even proceed — this is generally fast, from the Performance & Architecture chapter of this guide, but it's not free, and it's now on the critical path of literally every single request. A more complex rate-limiting algorithm, like the sliding-window or token-bucket implementations from earlier in this chapter, does genuinely more work per check than the simple fixed-window approach — worth weighing that added precision against its added cost for genuinely very high-traffic endpoints.

🔧 How to Keep This Reasonable​

Keep the Redis operations involved in a rate-limit check as small and efficient as possible, favoring INCR/EXPIRE or a tightly written Lua script over anything heavier, and ensure the Redis instance backing the rate limiter itself has the capacity to handle this added, constant load reliably.

💎 Good to Know: This Is the Same Read/Complexity Trade-off Covered Generally Throughout This Guide​

Choosing the simplest algorithm that genuinely meets the actual precision requirement, rather than defaulting to the most sophisticated option available, is the same underlying judgment call covered throughout this guide — a fixed-window limiter's boundary imprecision, from earlier in this chapter, may be a perfectly acceptable trade for its lower overhead on an endpoint where exact precision isn't actually critical.

9. How would you design a rate limiter for an API that needs different limits for different endpoints or user tiers?​

📖 Introduction​

This closing question combines every concept from this chapter into one realistic, production-shaped design.

🔧 Design​

Include both the identifying dimension, user or API key, from earlier in this chapter, and the specific endpoint or resource being rate-limited as part of the Redis key — ratelimit:user123:POST:/orders, for example — so different endpoints are tracked and limited entirely independently of each other. Look up the actual limit to apply based on the requesting user's tier, a free-tier user and a paid-tier user checked against genuinely different limit values, rather than a single, hardcoded limit shared by everyone. Choose the underlying algorithm, fixed window, sliding window, or token bucket, all from earlier in this chapter, based on how much precision each specific endpoint's actual risk profile genuinely warrants — a sensitive, expensive endpoint might justify sliding window's extra precision, while a low-stakes one is fine with fixed window's simplicity.

💎 Good to Know: Every Individual Piece of This Design Was Already Covered Earlier in This Chapter​

Just as with the closing questions in several other chapters throughout this guide, the actual skill being tested here is combining key design, tier-aware limits, and algorithm choice into one coherent, production-realistic system — not learning anything genuinely new in this final question.
