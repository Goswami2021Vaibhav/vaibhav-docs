Caching Strategies

1. What is cache-aside (lazy loading), and how does it decide when data actually gets loaded into the cache?​

📖 Introduction​

Cache-aside is the most commonly used caching pattern in practice, and the most natural starting point for this chapter.

🔄 What It Is​

The application checks the cache first — on a hit, it uses the cached value directly; on a miss, it fetches the data from the underlying database, returns it to the caller, and also writes it into the cache for next time.

async function getUser(id) {
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached);

  const user = await db.users.findById(id);
  await redis.set(`user:${id}`, JSON.stringify(user), "EX", 3600);
  return user;
}

🎯 When Data Actually Gets Loaded​

Only lazily, in response to an actual cache miss — data that's never requested is simply never loaded into the cache at all, which is exactly why this pattern is also called lazy loading.

💎 Good to Know: The Cache and the Database Can Briefly Disagree Under This Pattern​

Since the cache is only populated reactively, on a miss, there's a genuine window right after a miss where a concurrent request could also miss and also go fetch from the database — the cache-stampede question later in this chapter covers exactly this scenario.

2. What is write-through caching, and how does it differ from cache-aside in terms of when the cache gets populated?​

📖 Introduction​

Write-through flips the timing of cache population from reactive to proactive.

✍️ What It Is​

Every write to the underlying database is also, as part of that same write operation, written to the cache — the cache is always kept in sync with the database at write time, rather than waiting for a later read to populate it.

async function updateUser(id, data) {
  await db.users.update(id, data);
  await redis.set(`user:${id}`, JSON.stringify(data), "EX", 3600);
}

🆚 How It Differs From Cache-Aside​

Cache-aside, from the previous question, only populates the cache in reaction to a read that missed. Write-through populates the cache proactively, at write time, meaning a subsequent read is far more likely to already find a fresh, correct value waiting in the cache.

💎 Good to Know: Write-Through Trades Slightly Slower Writes for Consistently Fresher Reads​

Every write now does two things instead of one, database and cache, from earlier in this chapter, which adds a small amount of latency to each write — a reasonable trade specifically when reads are frequent and genuinely benefit from rarely, if ever, missing the cache.

3. What is write-behind (write-back) caching, and what risk does it introduce in exchange for its performance benefit?​

📖 Introduction​

Write-behind takes write-through's proactive population and defers the expensive part.

✍️ What It Is​

A write is applied to the cache immediately, and the corresponding write to the underlying database is deferred, batched, and applied asynchronously afterward, rather than as part of the same synchronous operation the caller waits on.

⚡ The Performance Benefit​

The caller only waits on the fast cache write, not the slower database write, from write-through's discussion earlier in this chapter — writes can feel dramatically faster from the application's perspective.

⚠️ The Risk It Introduces​

If the Redis instance holding that not-yet-persisted write fails before the deferred database write actually happens, that data is genuinely lost — the database never receives it, and the cache that held it is gone.

💎 Good to Know: This Is a Direct, Concrete Trade-off Between Performance and Durability​

This pattern is a specific, concrete instance of the general performance-versus-durability trade-off previewed in the Introduction & Fundamentals chapter of this guide — write-behind is only appropriate when that risk of losing a small, recent window of writes is genuinely acceptable for the specific data involved.

4. What is cache invalidation, and why is it often called one of the hardest problems in caching?​

📖 Introduction​

This is a genuinely famous phrase in computer science for a reason — invalidation is where caching's simplicity quietly runs out.

🔄 What It Is​

The process of removing or updating cached data once the underlying source data has changed, so the cache doesn't keep serving a now-outdated value.

🤔 Why It's Genuinely Hard​

Knowing precisely when data has changed, and ensuring every single write path that could change it also correctly triggers the matching invalidation, is easy to get subtly wrong — a write path that updates the database directly, an admin tool, a background job, a different service, but forgets to also invalidate the corresponding cache entry leaves stale data sitting there with no obvious signal that anything is wrong.

💎 Good to Know: This Is the Redis-Specific Instance of a Problem Covered Generally Elsewhere in This Repo​

This exact difficulty is covered generally in the Production Scenario Questions guide's Caching & Redis Scenarios chapter — the missing-invalidation-on-a-second-write-path scenario covered there is precisely this problem showing up as a real, concrete production incident.

5. What is a cache stampede, and how would you prevent one in a Redis-backed cache?​

📖 Introduction​

This connects directly to the window flagged at the end of the cache-aside question earlier in this chapter.

🐘 What It Is​

When a popular cache key expires or is invalidated, and a large number of concurrent requests all miss the cache at nearly the same moment, all of them independently hitting the underlying database at once — potentially overwhelming it.

🔧 How to Prevent It​

Ensure only one request actually recomputes and refills the cache on a miss, while other concurrent requests either briefly wait for that refill or are served a slightly stale value in the meantime, rather than every single one independently querying the database. Add a small amount of random jitter to TTLs, from later in this chapter, so that many keys with similar popularity don't all expire at the exact same instant.

💎 Good to Know: This Is the Exact Same Failure Mode Covered Generally in the Production Scenario Questions Guide, Now With Redis's Own Concrete Mechanics​

The Production Scenario Questions guide's Caching & Redis Scenarios chapter covers this same failure mode and its fixes generally — this question is that same concept, grounded specifically in Redis as the caching layer in question.

6. How would you decide what TTL to set for a given cached value?​

📖 Introduction​

There's no universally correct TTL — the right value depends on the specific data's own characteristics.

🎯 What to Consider​

How often the underlying data actually changes — data that changes rarely can tolerate a long TTL with little real risk of serving something meaningfully outdated. How costly serving stale data actually is for this specific use case — a slightly outdated list of product categories is a very different risk than a stale account balance. How expensive the data is to recompute or refetch from the database — a genuinely expensive query justifies a longer TTL to actually realize caching's benefit, since a very short TTL barely reduces load on an expensive underlying query.

🔧 Setting a TTL in Redis​

SET user:1:profile "{...}" EX 3600

💎 Good to Know: TTL Alone and Explicit Invalidation Alone Both Have Real Weaknesses — Using Both Together Is the More Resilient Default​

A long TTL with no explicit invalidation risks staying stale too long if nothing else refreshes it; explicit invalidation with no TTL as a backstop risks a bug in the invalidation logic leaving stale data cached indefinitely — pairing both, from the invalidation question earlier in this chapter, is generally the safer combination.

7. What's the difference between caching an entire object versus caching individual fields of it?​

📖 Introduction​

This is a genuinely practical design decision that connects directly to the Data Types chapter of this guide.

📦 Caching the Entire Object​

Storing the whole object as a single serialized String value, from the Data Types chapter of this guide — simple to work with, but any single field change requires re-serializing and rewriting the entire value.

🧩 Caching Individual Fields​

Storing the object as a Redis Hash, from the Data Types chapter of this guide, with each field cached separately — lets you update or read one specific field without touching the rest, at the cost of a slightly more involved read when you genuinely need the whole object back together.

🎯 How to Decide​

If the object is almost always read and written as a whole, a single serialized String is simpler and perfectly reasonable. If specific individual fields change frequently and independently of the rest, a Hash avoids the overhead of rewriting the entire object just to update one small piece of it.

💎 Good to Know: This Decision Mirrors the Embedding-vs-Referencing Reasoning From This Repo's MongoDB Guide​

Whole-object-versus-per-field caching here is a genuinely similar shape of trade-off to the embed-versus-reference decision covered in this repo's MongoDB guide — access pattern, specifically how the data is actually read and written, is what should drive the decision in both cases.

8. How do you handle a cache miss gracefully without overwhelming the underlying data source?​

📖 Introduction​

This question is about the moment right after a miss, before the cache has been refilled.

🔧 How to Handle It Gracefully​

Fetch the data from the underlying source, from cache-aside's flow earlier in this chapter, but guard against the stampede scenario from earlier in this chapter if the missed key is genuinely popular — coordinating so only one request does the actual fetch. If the underlying source is itself struggling or unavailable, consider whether serving a slightly stale, previously cached value, if one's available, is preferable to failing the request outright — directly related to the graceful-degradation reasoning covered in the Production Scenario Questions guide's Caching & Redis Scenarios chapter.

💎 Good to Know: A Cache Miss Shouldn't Be Treated as an Exceptional, Rare Event Requiring No Real Handling​

A cache miss is a completely normal, expected occurrence, not an edge case — treating it as something requiring no deliberate handling at all is exactly what leaves a system vulnerable to the stampede scenario, from earlier in this chapter, the moment a popular key happens to expire.

9. What are common mistakes developers make when introducing Redis caching into an existing application?​

📖 Introduction​

Most of these mistakes come from treating caching as a purely additive change with no real design considerations of its own.

❌ No TTL at All​

Caching data with no expiration, from the earlier TTL question in this chapter, meaning it can silently grow stale indefinitely with nothing ever refreshing it.

❌ Missing Invalidation on a Second Write Path​

Exactly the scenario covered in the invalidation question earlier in this chapter and in the Production Scenario Questions guide — a write path that updates the database but forgets to also invalidate the cached copy.

❌ Caching Data That Changes Too Frequently to Actually Benefit​

Adding caching to data that's read and written at roughly the same rate provides little real benefit while adding genuine complexity — caching pays off specifically for data read far more often than it changes.

❌ Not Planning for a Cache Outage​

Assuming the cache will always be available, rather than designing a graceful fallback to the underlying source if it's ever down, from the Production Scenario Questions guide's Caching & Redis Scenarios chapter.

💎 Good to Know: Nearly Every Mistake Here Traces Back to Treating Caching as "Free" Rather Than a Real Design Decision​

Every item on this list comes from adding caching without deliberately thinking through TTL, invalidation, access pattern, and failure behavior — exactly the four considerations this entire chapter has been building toward.

10. How would you design a caching layer for a read-heavy endpoint that's currently hitting the database on every request?​

📖 Introduction​

This closing question pulls together every concept from this chapter into one applied, end-to-end design.

🔧 Design​

Use cache-aside, from earlier in this chapter, as the default pattern — check Redis first, fall back to the database on a miss, and populate the cache on the way back out. Choose a TTL, from earlier in this chapter, based on how often the underlying data actually changes and how costly staleness genuinely is for this specific endpoint. Guard against a stampede, from earlier in this chapter, if this endpoint is popular enough that many concurrent requests could plausibly miss at once. Add explicit invalidation, from earlier in this chapter, on whatever write path actually changes this data, rather than relying purely on the TTL to eventually catch up.

💎 Good to Know: This Design Combines Every Individual Piece Covered Throughout This Chapter Into One Coherent Whole​

Cache-aside for the read path, a deliberately chosen TTL, stampede protection, and explicit invalidation on write — this closing question's actual test is whether you'd combine all four deliberately, rather than reaching for just one and calling the caching layer done.
