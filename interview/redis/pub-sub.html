Pub/Sub

1. What is the Redis Pub/Sub model, and how do publishers and subscribers interact through a channel?​

📖 Introduction​

Pub/Sub is Redis's built-in messaging pattern, genuinely distinct from anything covered in the Data Types chapter of this guide.

📡 What It Is​

A messaging model where publishers send messages to a named channel, and any clients currently subscribed to that channel receive the message immediately — publishers and subscribers never communicate directly with each other, only through the channel itself.

SUBSCRIBE notifications
PUBLISH notifications "New order received"

🎯 How the Interaction Works​

A publisher doesn't need to know who, or how many clients, are actually subscribed — it simply publishes to a channel name. Every currently connected subscriber to that exact channel receives the message the moment it's published.

💎 Good to Know: This Is a Genuinely Different Mechanism From Every Data Type Covered in This Guide So Far​

Every data type covered in the Data Types chapter of this guide is about storing and retrieving data — Pub/Sub isn't about storage at all, it's a live, in-the-moment messaging mechanism, which is exactly why the next question's answer is so important to understand clearly.

2. What happens to a message if it's published but no client is currently subscribed to that channel?​

📖 Introduction​

This is the single most important, and most commonly surprising, fact about Redis Pub/Sub.

💨 What Happens​

The message is simply gone — Redis Pub/Sub doesn't store or queue messages anywhere. If no client happens to be subscribed to the channel at the exact moment a message is published, that message is never delivered to anyone, and there's no way to retrieve it after the fact.

🎯 Why This Matters​

This is a fundamentally different guarantee than a message queue, from the next question, or a database write — Pub/Sub delivers a message only to whoever happens to already be listening at that precise moment, with zero persistence or replay capability built in.

💎 Good to Know: This Single Fact Explains Nearly Every Other Question in This Chapter​

Whether Pub/Sub is the right tool for a given use case, from later in this chapter, almost always comes down to this one property — if losing a message that nobody happened to be listening for is genuinely unacceptable for your use case, Pub/Sub alone isn't the right tool.

3. What's the difference between Redis Pub/Sub and a proper message queue in terms of delivery guarantees?​

📖 Introduction​

This question makes the previous one's implication fully explicit through direct comparison.

📡 Redis Pub/Sub​

No persistence, no delivery guarantee, no replay — a message only reaches subscribers who are actively connected at the exact moment it's published, from the previous question.

📬 A Proper Message Queue​

Messages are stored durably until a consumer actually processes and acknowledges them — a consumer that's temporarily offline will still receive queued messages once it reconnects, rather than having simply missed them forever.

🎯 Why This Distinction Matters​

Choosing Pub/Sub for a use case that genuinely needs guaranteed delivery is a real, common mistake — the two solve genuinely different problems, and the choice between them should be driven by whether missed messages are actually acceptable for the use case.

💎 Good to Know: Redis Streams, Covered Later in This Chapter, Sit Much Closer to a Proper Message Queue Than Pub/Sub Does​

This is exactly why the Data Types chapter of this guide introduced Streams as a more purpose-built alternative to a List for message-log use cases — Streams provide the persistence and consumer-tracking guarantees Pub/Sub deliberately doesn't.

4. What are pattern-based subscriptions, and what's a realistic use case for one?​

📖 Introduction​

Beyond subscribing to one exact channel name, Redis also lets you subscribe more broadly.

🎯 What They Are​

Using PSUBSCRIBE with a glob-style pattern, a client can subscribe to every channel whose name matches that pattern, rather than needing to subscribe to each specific channel individually.

PSUBSCRIBE room.*
PUBLISH room.42 "New message in room 42"

🎯 A Realistic Use Case​

A chat application with many dynamically created rooms — rather than the server needing to individually subscribe to every single room's channel as rooms are created, a single pattern subscription like room.* automatically catches messages published to any room channel, present or future.

💎 Good to Know: A Pattern Subscription Still Carries the Same Delivery Guarantees, or Lack Thereof, as a Normal One​

Pattern-based subscriptions are purely a convenience for matching multiple channel names — they don't change anything about the fundamental "must be subscribed at the moment of publish" limitation from earlier in this chapter.

5. Why is Redis Pub/Sub not a good fit for tasks that require guaranteed delivery or message persistence?​

📖 Introduction​

This question asks you to state plainly, in your own words, the conclusion the earlier questions in this chapter have been building toward.

⚠️ Why It's Not a Good Fit​

Pub/Sub has no concept of a message being stored, queued, or retried — it delivers, in real time, only to whoever's actively subscribed at that exact instant, from earlier in this chapter. A task that genuinely can't tolerate a lost message, processing a payment notification or a critical background job, needs the durability and retry semantics Pub/Sub deliberately doesn't provide.

🎯 What This Means in Practice​

Using Pub/Sub for anything where a missed message would be a real problem is a design mistake — that's precisely the kind of task Streams, from earlier in this chapter, or a dedicated message queue system, are built for instead.

💎 Good to Know: "Not a Good Fit" Doesn't Mean "Never Useful" — the Next Question Covers Where It Genuinely Shines​

This limitation doesn't make Pub/Sub a bad feature — it makes it the wrong tool for a specific category of task, while remaining an excellent fit for a different category covered in the next question.

6. How do Redis Streams, from the Data Types chapter of this guide, address some of Pub/Sub's limitations?​

📖 Introduction​

This question directly connects two chapters of this guide that are easy to conflate.

🔗 What Streams Add That Pub/Sub Lacks​

Persistence — a Stream stores its entries durably as an actual data structure, rather than only delivering to whoever's currently listening, from earlier in this chapter. Consumer groups and acknowledgment, from the Data Types chapter of this guide — a consumer that was briefly offline can still read entries it missed once it reconnects, and can explicitly acknowledge it processed an entry, neither of which Pub/Sub supports at all.

🎯 What This Means for Choosing Between Them​

If you genuinely need durability, replay, or acknowledgment, reach for Streams. If you genuinely just need live, real-time fan-out to whoever's currently listening, with no need to persist or replay anything, Pub/Sub, covered throughout this chapter, is simpler and perfectly suited.

💎 Good to Know: Streams and Pub/Sub Aren't Competing Implementations of the Same Idea — They're Different Tools for Different Guarantees​

This isn't "Streams are just a better version of Pub/Sub" — Pub/Sub's simplicity is a genuine advantage for the specific use cases covered in the next question, where Streams' added durability and complexity simply aren't needed.

7. What's a realistic use case where Redis Pub/Sub is genuinely the right tool despite its lack of delivery guarantees?​

📖 Introduction​

This question is about recognizing when Pub/Sub's core limitation, from earlier in this chapter, genuinely doesn't matter.

✅ A Realistic Use Case​

Live, in-the-moment notifications where a missed message truly has no lasting consequence — a "user is typing" indicator in a chat application, from this repo's Socket.IO guide's real-time context, or a live cursor position in a collaborative editing tool. If a client happens to be briefly disconnected and misses one of these updates, the very next one arrives moments later and is all that actually matters — there's no real cost to having missed the ones in between.

🎯 Why Pub/Sub Fits This Well​

The simplicity and low overhead of Pub/Sub, from earlier in this chapter, is a genuine advantage here, since the durability and consumer-tracking machinery Streams provide, from earlier in this chapter, would be pure, unneeded overhead for this kind of ephemeral, self-superseding update.

💎 Good to Know: "Does a Missed Message Actually Matter" Is the Single Question That Decides Pub/Sub vs. Streams​

This is the practical, one-question version of the entire Pub/Sub-versus-Streams decision covered throughout this chapter — if the answer is genuinely no, Pub/Sub is often the simpler, perfectly appropriate choice.

8. How would you use Redis Pub/Sub to broadcast an event across multiple application server instances?​

📖 Introduction​

This applied question covers one of Pub/Sub's most common real-world roles.

🎯 The Scenario​

Several application server instances, from the Scalability guide's horizontal-scaling discussion, each need to know when something happens, so they can, for example, push a real-time update to whichever of their own connected clients happen to care about it.

🔧 How Pub/Sub Solves This​

Every application server instance subscribes to a shared channel on startup. When any one instance needs to broadcast an event, it publishes to that channel, and every other instance, since they're all currently subscribed, receives it immediately and can then act on it locally — pushing it to its own connected clients, for example.

💎 Good to Know: This Is Exactly the Cross-Instance Coordination Mechanism Flagged in the Networking Guide's Web Communication Chapter​

The Networking guide's Web Communication chapter flags this exact need — letting one server instance's event reach a client connection actually held by a different instance — and names a shared pub/sub layer like Redis as the standard solution, which is precisely the mechanism this question walks through concretely.

9. What happens to a subscriber's messages if its connection briefly drops and reconnects?​

📖 Introduction​

This closing question makes the consequence of Pub/Sub's core limitation, from earlier in this chapter, fully concrete for a genuinely common, real scenario.

💨 What Happens​

Any messages published to the channel during the window the client was disconnected are simply lost to that client — Pub/Sub has no memory of what was published while nobody happened to be listening, from earlier in this chapter, and reconnecting doesn't retrieve anything that was missed.

🎯 What an Application Needs to Do About It​

If missing messages during a brief disconnection is genuinely unacceptable, the application needs to either resynchronize its state through some other means after reconnecting, fetching current state directly rather than relying on having received every intermediate event, or use Streams, from earlier in this chapter, instead, specifically for the durability and replay this scenario needs.

💎 Good to Know: This Closing Scenario Is the Concrete, Real-World Payoff of This Entire Chapter's Central Warning​

Every earlier question in this chapter has been building toward exactly this practical consequence — a brief, completely normal network hiccup is all it takes to lose messages under Pub/Sub, which is why understanding this limitation upfront, before building on Pub/Sub, matters far more than discovering it the hard way in production.
