Transactions

1. What do MULTI and EXEC actually do in a Redis transaction?​

📖 Introduction​

"Transaction" means something genuinely narrower in Redis than it might suggest coming from a relational database — this chapter is about being precise about exactly what that is.

🔧 What They Do​

MULTI starts queuing up a sequence of commands rather than executing them immediately — each subsequent command is queued, not run, until EXEC is called, at which point every queued command executes, one after another, as a single, uninterrupted batch.

MULTI
SET key1 "value1"
INCR counter
EXEC

🎯 What This Achieves​

Every command between MULTI and EXEC is guaranteed to run back-to-back, with no other client's commands interleaved in between any of them — directly related to the single-threaded execution model covered in the Performance & Architecture chapter of this guide.

💎 Good to Know: Commands Are Only Queued, Not Validated for Correctness, Until EXEC Actually Runs Them​

Between MULTI and EXEC, commands are simply being collected — Redis doesn't actually execute or evaluate them until EXEC is called, which matters for understanding what kind of errors can, and can't, be caught before that point, covered later in this chapter.

2. In what sense is a Redis transaction different from a relational database transaction covered in this repo's SQL/MySQL guide?​

📖 Introduction​

This is the single most important distinction to get right in this entire chapter.

🆚 What a Relational Transaction Provides​

Full ACID guarantees, from this repo's SQL/MySQL and MongoDB guides — critically, genuine rollback: if one statement partway through a transaction fails, every change made so far within that transaction is automatically undone.

🆚 What a Redis Transaction Provides​

Every queued command is guaranteed to execute together, uninterrupted by other clients, from the previous question — but Redis does not automatically roll back previously executed commands within that same transaction if a later one fails, covered in more depth in the next question.

💎 Good to Know: "Transaction" in Redis Really Means "Batched, Uninterrupted Execution," Not "All-or-Nothing With Rollback"​

Coming from a relational or MongoDB background, from this repo's respective guides, the word "transaction" naturally implies automatic rollback on failure — Redis's actual guarantee is narrower, and this mismatch in expectation is exactly what the next question covers concretely.

3. Does Redis support rolling back a transaction if one of its commands fails?​

📖 Introduction​

This directly answers the gap flagged at the end of the previous question, with the actual concrete behavior.

❌ No Automatic Rollback​

If a command within an executing transaction fails partway through, for a reason Redis couldn't have caught before running it, applying an operation to a value of the wrong type, for instance, the commands before it have already taken effect, and the commands after it still execute — Redis does not undo anything that already ran.

🎯 Why This Differs From What "Transaction" Usually Implies​

Redis's transaction guarantee is specifically about atomicity of execution order — uninterrupted, back-to-back running, from earlier in this chapter — not atomicity of outcome the way a relational database's automatic rollback provides, from the previous question.

💎 Good to Know: Errors Caught Before EXEC vs. Errors That Only Surface During Execution Are Handled Differently​

A command with an obviously malformed syntax is rejected at queue time, before MULTI/EXEC even runs, and Redis will refuse to execute the entire transaction at all in that case — but an error that only becomes apparent once a command actually runs against real data, like a type mismatch, still lets every other queued command execute regardless.

4. What is WATCH, and how does it provide optimistic locking within a Redis transaction?​

📖 Introduction​

WATCH is Redis's tool for a conditional transaction — one that should only actually proceed if certain data hasn't changed underneath it.

👀 What It Is​

A command that tells Redis to monitor a specific key for changes — if you call WATCH on a key before starting a transaction with MULTI, and that key is modified by any other client before you call EXEC, the entire transaction is aborted rather than executed.

WATCH balance
val = GET balance
MULTI
SET balance (val - 100)
EXEC

🔒 How It Provides Optimistic Locking​

Rather than locking the key to prevent any other client from touching it while you decide what to do, WATCH lets everyone proceed freely, and only checks at the very last moment, EXEC, whether the data you based your transaction on is still current — the same optimistic-concurrency philosophy covered generally in the Production Scenario Questions guide's Database Scenarios chapter.

💎 Good to Know: WATCH Is What Makes "Read, Then Conditionally Write" Safe Under Concurrency​

Without WATCH, reading a value, deciding what to write based on it, and then writing it back in a separate transaction is exactly the kind of read-modify-write race condition covered generally throughout this repo — WATCH is Redis's specific mechanism for closing that gap.

5. What happens if a watched key changes between WATCH and EXEC?​

📖 Introduction​

This is the direct, concrete payoff of the previous question's mechanism.

⚠️ What Happens​

EXEC returns a null response indicating the transaction was aborted — none of the queued commands execute at all, since the data the transaction's logic was based on is no longer current.

🔧 What the Application Should Do Next​

Detect this null response and retry the entire operation from the beginning — re-reading the current value and re-attempting the WATCH/MULTI/EXEC sequence — rather than assuming the transaction succeeded.

💎 Good to Know: This Retry Pattern Is Conceptually the Same as Handling a Write Conflict in a MongoDB Transaction​

This directly parallels the write-conflict retry pattern covered in this repo's MongoDB guide's Transactions chapter — both represent a concurrency-safety mechanism detecting a conflicting change and requiring the application to retry, rather than silently proceeding on stale data.

6. Why are all commands within a Redis transaction guaranteed to execute without another client's commands interleaving?​

📖 Introduction​

This question ties the transaction guarantee directly back to a concept from earlier in this guide.

🔒 Why the Guarantee Holds​

Redis executes commands one at a time on a single thread, from the Performance & Architecture chapter of this guide — once EXEC runs, every queued command within that transaction executes back-to-back on that same single thread, with no opportunity for the thread to switch away and process a different client's command in between any of them.

🎯 Why This Guarantee Is "Free" in Redis​

Unlike a relational database, which needs explicit locking or isolation mechanisms to guarantee this kind of non-interleaved execution, Redis gets it automatically, as a direct structural consequence of its single-threaded design — the same underlying reason individual commands are inherently atomic, from the Performance & Architecture chapter of this guide.

💎 Good to Know: This Guarantee Is About Execution Order, Not About the Broader Rollback Semantics Covered Earlier in This Chapter​

It's worth keeping this specific guarantee, uninterrupted execution order, clearly separate in your mind from the rollback behavior covered earlier in this chapter — the two are genuinely different properties, and conflating them is exactly the common misunderstanding this chapter has been addressing.

7. What's the difference between using a Redis transaction and using a Lua script, from the Performance & Architecture chapter of this guide, to achieve atomicity?​

📖 Introduction​

Both provide atomic, uninterrupted execution of multiple operations — the real difference is in what each one can actually do while executing.

🔒 A Redis Transaction​

Queues a fixed, predetermined batch of commands, from earlier in this chapter, and runs them together — but the transaction itself can't make a decision based on data it reads mid-transaction; each queued command is fixed in advance.

📜 A Lua Script​

Can read data, branch on conditions, and decide what to do next, all within the same atomic, uninterrupted execution, from the Performance & Architecture chapter of this guide — genuinely more expressive for logic that depends on a value it looks up along the way.

🎯 When to Reach for Each​

A transaction fits a straightforward, fixed batch of commands. A Lua script fits logic that genuinely needs to branch or compute based on data read during that same atomic execution — something a transaction, with its fixed, pre-queued command list, can't do on its own.

💎 Good to Know: WATCH-Based Conditional Logic and Lua Scripting Solve a Similar Problem in Different Ways​

Both WATCH, from earlier in this chapter, and a Lua script let you make a transaction's outcome depend on the data's current state — WATCH does it by aborting if data changed since you last checked it; a Lua script does it by directly reading and branching on the data within the atomic execution itself, a more powerful but also more involved approach.

8. What are the practical limitations of Redis transactions compared to what "transaction" implies in a relational database?​

📖 Introduction​

This closing-comparison question distills the entire chapter into one direct list.

⚠️ The Limitations​

No automatic rollback on a mid-transaction failure, from earlier in this chapter — a relational database's core transactional promise Redis simply doesn't provide. No genuine isolation levels to choose from — Redis's guarantee is closer to always running each transaction back-to-back and uninterrupted, rather than offering a spectrum of configurable isolation trade-offs. Conditional behavior depends on WATCH, from earlier in this chapter, an optimistic mechanism requiring an explicit retry on conflict, rather than a database automatically blocking or serializing conflicting transactions for you.

💎 Good to Know: None of This Makes Redis Transactions Useless — It Makes Them a Narrower, Different Tool​

These limitations don't mean Redis transactions aren't valuable — they mean the word "transaction" is doing less work here than it does in a relational database, and understanding exactly how much less is the actual point of this entire chapter.

9. When would you reach for a Redis transaction versus a single atomic command like INCR?​

📖 Introduction​

This closes the chapter by asking when the machinery covered throughout it is actually needed at all.

✅ When a Single Atomic Command Is Already Enough​

Whenever the operation is genuinely expressible as one built-in Redis command — INCR, from the Data Types chapter of this guide, is already fully atomic on its own; wrapping it in MULTI/EXEC adds no additional guarantee it didn't already have.

✅ When a Transaction Is Actually Needed​

When you genuinely need several separate commands to execute together, uninterrupted, from earlier in this chapter — updating two different keys as part of the same logical operation, for example — where no single built-in command already covers the whole thing atomically on its own.

💎 Good to Know: Reaching for MULTI/EXEC When a Single Command Already Suffices Is Unnecessary Complexity​

Just as with reaching for a full multi-document transaction in MongoDB when single-document atomicity already covers the need, from this repo's MongoDB guide, wrapping a single already-atomic Redis command in a transaction adds complexity without adding any actual additional guarantee — worth reaching for MULTI/EXEC only once a genuine multi-command need actually exists.
