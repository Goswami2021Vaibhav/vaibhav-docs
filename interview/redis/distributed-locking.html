Distributed Locking

1. What problem does a distributed lock solve that a normal, in-process lock can't?​

📖 Introduction​

This chapter is the first of two "practical pattern" chapters built on top of everything covered so far in this guide.

🔒 What a Normal, In-Process Lock Solves​

Coordinating access to a shared resource between multiple threads within the same single process — a mutex or similar construct ensures only one thread at a time can enter a critical section of code.

🌐 What a Normal Lock Can't Solve​

Once an application runs as multiple separate processes, potentially on entirely different machines, from the Scalability guide's horizontal-scaling discussion, an in-process lock is useless — each process has its own separate memory and its own separate lock, with no shared awareness of what any other process is doing at all.

🎯 What a Distributed Lock Solves​

Coordinating access to a shared resource across multiple independent processes, potentially running on entirely different machines, by using something all of them can see and agree on — Redis, being fast and centrally reachable by every instance, is a natural fit for exactly this coordination point.

💎 Good to Know: This Is the Same Fundamental Need Rate Limiting, Covered Next in This Guide, Also Has​

The next chapter's need for a rate limiter to work consistently across multiple application server instances is really the same underlying problem — needing shared, agreed-upon state that no single instance's local memory can provide on its own.

2. How would you implement a basic distributed lock using a single Redis instance?​

📖 Introduction​

The core mechanism is genuinely simple — the sophistication in this chapter comes from handling its edge cases correctly.

🔧 Basic Implementation​

Use SET with the NX (only set if the key doesn't already exist) option to atomically acquire the lock — if the key is successfully set, you hold the lock; if it already existed, someone else does.

SET lock:order:501 "process-A-id" NX EX 10

🎯 Why NX Is the Key Piece​

SET ... NX is a single atomic operation, from the Performance & Architecture chapter of this guide — checking whether the key exists and setting it happen as one indivisible step, meaning two processes racing to acquire the same lock can never both succeed, the same atomicity guarantee that makes INCR, from the Data Types chapter of this guide, safe under concurrency.

💎 Good to Know: A Non-Atomic "Check, Then Set" Approach Would Reintroduce the Exact Race Condition This Is Meant to Prevent​

Checking whether the key exists with a separate GET first, and only then calling SET if it doesn't, reopens a window where two processes could both see the key as absent and both proceed to set it — exactly why NX as a single atomic command, not two separate steps, is the actual point of this implementation.

3. Why does a distributed lock need an expiration, and what happens if you forget to set one?​

📖 Introduction​

The EX 10 in the previous question's example isn't incidental — it's a critical, deliberate part of the design.

⚠️ Why It's Needed​

If the process holding the lock crashes, or is unable to release it for any reason, from the later question in this chapter, a lock with no expiration would simply stay held forever — no other process could ever acquire it again, a permanent deadlock over that resource.

🎯 What an Expiration Does​

Guarantees the lock is automatically released after some maximum reasonable time, using the TTL mechanism covered in the Expiration & Eviction chapter of this guide, even if the process that acquired it never explicitly releases it itself.

💎 Good to Know: Choosing the Expiration Duration Is Itself a Real Trade-off​

Too short, and the lock might expire while the process is still legitimately using the resource, letting a second process acquire it prematurely; too long, and a crashed process's lock stays uselessly held for an unnecessarily long time — this tension is exactly why more sophisticated approaches, like extending a lock's TTL while work is still genuinely in progress, exist in more advanced implementations.

4. What is the Redlock algorithm, and what problem does it solve that a single-instance lock doesn't?​

📖 Introduction​

Redlock addresses a specific weakness in relying on just one Redis instance for something as consequential as a lock.

⚠️ The Problem With a Single Instance​

If the single Redis instance holding the lock, from earlier in this chapter, becomes unavailable, even briefly, or if it's part of a replicated setup and a failover, from the Replication & High Availability chapter of this guide, happens at just the wrong moment, the lock's state could become unreliable — a newly promoted replica might not yet have the lock recorded on it, from the replication-lag discussion in that same chapter, letting a second process incorrectly acquire what it believes is a free lock.

🔧 What Redlock Does​

Requires acquiring the lock across a majority of several genuinely independent Redis instances, rather than trusting just one — a lock is only considered successfully held if a majority of those independent instances agree it was acquired, similar in spirit to the quorum concept covered in the Replication & High Availability chapter of this guide.

💎 Good to Know: Redlock Trades Simplicity for Resilience Against a Single Instance's Own Failure​

This is a deliberate, more involved design specifically to avoid a single point of failure being able to compromise the lock's correctness — the added complexity is the direct cost of that stronger guarantee, echoing the same "more resilience costs more operational complexity" theme running throughout this guide.

5. What's a realistic scenario where two processes could both believe they hold the same lock, and how does proper implementation prevent it?​

📖 Introduction​

This question grounds the abstract risk covered so far in this chapter in one concrete, illustrative scenario.

⚠️ A Realistic Scenario​

Process A acquires the lock and begins its work, but takes longer than the lock's configured TTL, from earlier in this chapter, perhaps due to an unexpectedly slow downstream call. The lock expires automatically while Process A is still working, and Process B, seeing the key now absent, successfully acquires the very same lock — for a brief window, both processes now believe they hold it, and both proceed to act on the shared resource simultaneously.

🔧 How Proper Implementation Prevents It​

Setting a genuinely realistic TTL relative to how long the protected work actually takes, from earlier in this chapter, and, for work with unpredictable duration, having the lock holder periodically extend its own TTL while work is still legitimately in progress, rather than relying on a single, fixed, one-shot expiration.

💎 Good to Know: This Scenario Is Exactly Why "Just Add a TTL" Isn't the Whole Story​

A TTL solves the crashed-process deadlock problem, from earlier in this chapter, but introduces this exact new risk if it's not sized thoughtfully relative to the real, actual duration of the work being protected — both considerations have to be weighed together, not just the first one in isolation.

6. Why is it important that only the process that acquired a lock is the one that releases it?​

📖 Introduction​

This covers a subtle but genuinely important correctness requirement that's easy to get wrong.

⚠️ The Risk of Getting This Wrong​

If any process can release any lock, regardless of who acquired it, then in the exact scenario from the previous question, Process A could finish its (now-expired) work and mistakenly release what is actually Process B's currently legitimate lock — freeing a lock a different process is genuinely, correctly relying on.

🔧 How to Ensure Only the Rightful Owner Releases It​

Store a unique identifier, from the earlier SET ... NX example in this chapter, alongside the lock, and only release it if the value currently stored still matches the identifier the releasing process originally set — typically done atomically with a Lua script, from the Transactions chapter of this guide, so the check-and-delete happens as one indivisible operation.

if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end

💎 Good to Know: This Is the Same "Check, Then Act, Atomically" Principle Used Throughout This Chapter​

Verifying ownership and releasing the lock have to happen as a single atomic operation, exactly like the acquisition step earlier in this chapter — doing them as two separate steps would reopen the same kind of race condition this entire chapter has been carefully closing at every stage.

7. What happens if a process holding a lock crashes before releasing it?​

📖 Introduction​

This closes the loop on the very first question's motivating problem, now with the full mechanism in place.

💥 What Happens​

Without any TTL, from earlier in this chapter, the lock would remain held forever, since the process that would normally release it can no longer do so — a permanent deadlock. With an appropriately configured TTL, the lock simply expires automatically once that TTL is reached, and becomes available for another process to acquire.

🎯 Why This Is Considered an Acceptable Outcome​

A crashed process was, by definition, not actually going to finish its protected work correctly anyway — automatically releasing the lock after a reasonable timeout, rather than leaving it permanently stuck, is the more useful behavior for the rest of the system, even though it does introduce the risk covered in the earlier scenario question in this chapter if the TTL is misjudged.

💎 Good to Know: This Is Precisely Why the TTL-Sizing Trade-off From Earlier in This Chapter Matters​

This scenario, and the earlier one where a still-working process's lock expires prematurely, are really the two opposite failure modes of the exact same TTL decision — too short favors this scenario's fast recovery at the risk of the earlier one; too long favors avoiding the earlier one at the cost of a longer deadlock here.

8. What are the known criticisms of using Redis for distributed locking in genuinely critical scenarios?​

📖 Introduction​

This question asks you to represent a genuine, real debate within the Redis and distributed-systems community honestly.

⚠️ The Core Criticism​

Some well-known distributed-systems experts have argued that even Redlock, from earlier in this chapter, doesn't provide a strong enough correctness guarantee for scenarios where a lock's correctness is genuinely, critically important — clock behavior across independent servers, process pauses, and network delays can, in specific edge cases, still allow two processes to briefly both believe they hold the same lock, despite Redlock's majority-based design.

🎯 What This Means in Practice​

For most everyday use cases, a Redis-based lock, implemented carefully with the safeguards covered throughout this chapter, is genuinely good enough. For scenarios where a lock failure would be genuinely catastrophic, financial transactions with no tolerance for double-processing, for instance, this criticism is a real reason to consider a system specifically designed with stronger, formally proven distributed-consensus guarantees instead.

💎 Good to Know: Acknowledging This Debate Honestly Is Itself a Sign of Senior-Level Understanding​

Being aware that this is a genuinely contested topic, rather than presenting Redis-based locking as an unconditionally solved problem, is exactly the kind of nuanced, honest answer that distinguishes a strong response to this chapter's closing question from a purely mechanical one.

9. How would you decide whether Redis-based locking is safe enough for a specific use case, or whether a different tool is warranted?​

📖 Introduction​

This closing question turns the previous question's honest caveat into an actual, practical decision framework.

🔍 What to Consider​

How costly a genuine failure of the lock's guarantee would actually be — a brief, rare double-execution of a low-stakes background job is a very different risk than two processes both believing they hold a lock over a financial transaction, from the previous question. How much additional complexity and operational cost a stronger-guarantee alternative would actually add, weighed against how much that added protection is genuinely worth for this specific use case.

🎯 A Practical Default​

For the overwhelming majority of everyday coordination needs, a carefully implemented Redis lock, using the safeguards covered throughout this chapter, TTLs sized appropriately, unique ownership tokens, atomic release, is genuinely sufficient. Reach for a more heavyweight, formally guaranteed alternative specifically once the earlier question's criticism's edge cases would actually be unacceptable for the specific stakes involved.

💎 Good to Know: This Closing Question Applies the Same "Match the Tool to the Actual Stakes" Reasoning Used Throughout This Repo​

This is the same underlying judgment call covered throughout this repo — from choosing UDP over TCP in the Networking guide to deciding whether a MongoDB transaction is genuinely needed in this repo's MongoDB guide — matching a tool's actual guarantees to what the situation genuinely requires, rather than defaulting to either extreme.
