Replication & Sharding

1. What is a replica set, and what roles do the primary and secondary nodes each play?​

📖 Introduction​

This chapter fully covers the replication-versus-sharding distinction previewed in the Performance Optimization chapter of this guide.

🧩 What a Replica Set Is​

A group of MongoDB servers that each maintain a copy of the same data, working together to provide redundancy and high availability.

👑 Primary Node​

The single node within a replica set that accepts all write operations at any given time, applying each write and then streaming it to the secondary nodes.

📄 Secondary Nodes​

Nodes that continuously replicate the primary's writes, keeping their own copy of the data up to date, and can optionally serve read traffic, from the read-preferences question later in this chapter, but don't accept writes directly themselves.

💎 Good to Know: A Replica Set Typically Has an Odd Number of Members​

Configuring an odd number of members, three being the common default, is a deliberate choice that supports the primary-election mechanism covered in the next question — an odd number avoids the possibility of a tied vote when the replica set needs to agree on a new primary.

2. How does automatic failover work when a replica set's primary node goes down?​

📖 Introduction​

This is the core high-availability payoff a replica set actually provides.

🔄 How Failover Works​

The remaining secondary nodes detect that the primary is no longer reachable, and hold an election among themselves to choose a new primary from the eligible secondaries — once a new primary is elected, the replica set resumes accepting writes through it, and the previous primary, if and when it comes back online, rejoins the set as a secondary.

🎯 Why This Matters​

This process happens automatically, without requiring manual intervention, meaning a replica set can continue serving both reads and writes through a newly elected primary even after losing its original one — the entire mechanism this chapter's high-availability framing is built around.

💎 Good to Know: Failover Isn't Instantaneous — There's a Brief Window Where Writes Aren't Accepted​

Detecting the primary's failure and completing an election takes a genuinely brief amount of time, during which the replica set temporarily can't accept new writes — a real, if usually short, availability gap worth being aware of rather than assuming failover is perfectly seamless.

3. What are read preferences, and how do they let you trade off consistency for read performance?​

📖 Introduction​

Read preferences are the mechanism that actually lets you use secondary nodes for something beyond pure redundancy.

📖 What They Are​

A setting that controls which member of a replica set a given read operation is actually allowed to be served from — the primary only, a secondary, or some more nuanced preference between the two.

⚖️ The Trade-off​

Reading from the primary always reflects the absolute latest committed writes. Reading from a secondary can distribute read load across more than just the primary, from the Performance Optimization chapter of this guide, but risks reading slightly stale data, due to replication lag, covered generally in the Production Scenario Questions guide's Database Scenarios chapter — the secondary might not have yet applied the very latest writes from the primary.

💎 Good to Know: This Is the Same Read-Freshness Trade-off Covered Generally Elsewhere in This Repo, Now With MongoDB's Specific Lever​

The Production Scenario Questions guide covers replication lag and its implications generally — read preferences are the specific, concrete MongoDB setting that lets you deliberately choose where on that freshness-versus-load-distribution trade-off a given read should sit.

4. What is sharding, and what problem does it solve that replication alone doesn't?​

📖 Introduction​

This directly follows up on the replication-versus-sharding preview from the Performance Optimization chapter of this guide.

🧩 What It Is​

A technique for distributing a collection's data across multiple servers, called shards, so that no single server needs to hold the entire dataset or handle the entire write load on its own.

🎯 What It Solves That Replication Doesn't​

Replication, from earlier in this chapter, gives every member of a replica set essentially the same full copy of the data — it improves availability and read distribution, but doesn't help once the dataset itself becomes too large for a single server to hold, or the write volume becomes too high for a single primary node to handle. Sharding solves specifically that problem, by splitting the data itself, and the associated write load, across multiple independent servers.

💎 Good to Know: Replication and Sharding Are Commonly Used Together, Not as Alternatives​

A production sharded cluster typically has each individual shard itself running as its own replica set, from earlier in this chapter — sharding for capacity and write throughput, replication within each shard for that shard's own availability, both operating simultaneously rather than as competing choices.

5. What is a shard key, and why is choosing a good one one of the most consequential decisions in a sharded deployment?​

📖 Introduction​

The shard key is the single decision that determines almost everything about how well a sharded cluster actually performs.

🔑 What It Is​

A field, or combination of fields, chosen from a collection's documents that MongoDB uses to determine which shard a given document actually lives on.

🎯 Why It's So Consequential​

Every document with a given shard key value lands on a predictable, specific shard based on that value — which means the shard key directly determines how evenly data and traffic are distributed across the cluster, from the chunk-balancing question later in this chapter, and it's genuinely difficult to change after a collection has already grown large, since changing it effectively means redistributing the entire dataset.

💎 Good to Know: A Shard Key Decision Made Early Has Consequences That Compound as the Collection Grows​

This is one of the clearest cases in MongoDB of a decision that's cheap to get right early and expensive to fix later — directly related to the general "avoid choices that are cheap now but hard to reverse later" reasoning covered in the Production Scenario Questions guide's System Design Scenarios chapter.

6. What can go wrong with a poorly chosen shard key?​

📖 Introduction​

This is the concrete, negative payoff of the previous question's warning — worth understanding specifically what actually breaks.

⚠️ What Can Go Wrong​

A shard key with low cardinality, few distinct possible values, or a heavily skewed distribution of values, can cause most documents to land on just one or a few shards, leaving the others comparatively idle — genuinely defeating the entire purpose of sharding, since the cluster's capacity and throughput end up bottlenecked by that one overloaded shard anyway. A monotonically increasing shard key, like a simple incrementing counter or a raw creation timestamp, can cause all new writes to concentrate on whichever single shard currently holds the highest range of values, rather than spreading new write traffic evenly across the cluster.

🎯 Why This Matters in Practice​

Both failure modes result in a cluster that looks properly sharded on paper but doesn't actually deliver the distributed capacity and throughput sharding is supposed to provide — the entire benefit of sharding lives or dies on this one decision.

💎 Good to Know: A Good Shard Key Generally Has High Cardinality and Spreads Writes Evenly​

The general heuristic worth remembering is a shard key with many distinct values and no strong, ongoing bias toward one particular value range for new writes — both of the failure modes above are really the same underlying problem, uneven distribution, showing up in slightly different ways.

7. What is chunk balancing, and why does a sharded cluster need it?​

📖 Introduction​

Even with a well-chosen shard key, from the previous two questions, a sharded cluster still needs an ongoing mechanism to stay balanced over time.

📦 What It Is​

MongoDB divides a sharded collection's data into ranges called chunks, based on shard key values, and distributes those chunks across the available shards. A background balancer process periodically moves chunks between shards to keep the distribution roughly even as data is added, removed, or as the cluster's shards themselves change.

🎯 Why It's Needed​

Even a well-chosen shard key can drift out of even distribution over time as data grows unevenly, or as shards are added to or removed from the cluster — the balancer is what continuously corrects for this drift, rather than requiring manual, ongoing intervention to keep the cluster balanced.

💎 Good to Know: Balancing Has Its Own Real Resource Cost, Which Is Why It's Worth Being Aware Of, Not Just Assuming It's Free​

Moving chunks between shards involves actually transferring data over the network and updating routing information — this has a genuine, if usually modest, resource cost, which is why balancing activity is sometimes deliberately scheduled or throttled during lower-traffic windows in a genuinely high-traffic production deployment.

8. What's the fundamental difference between what replication and sharding each actually solve?​

📖 Introduction​

This closing comparison question distills the entire first half of this chapter into one clean, direct distinction.

🎯 The Fundamental Difference​

Replication solves for availability and read distribution — every replica set member holds essentially the full dataset, so losing one node doesn't mean losing the data, and read traffic can be spread across more than just the primary. Sharding solves for capacity and write throughput — splitting the data itself across multiple independent shards means no single server needs to hold or write the entire dataset alone.

🤝 Why Both Are Often Needed Together​

A large-scale, highly available production deployment typically needs both — sharding so the dataset and write load can grow beyond what any single server could handle, and replication within each shard so that any individual shard's failure doesn't cause data loss or an outage.

💎 Good to Know: "Replication for Availability, Sharding for Scale" Is the One-Line Summary Worth Remembering​

If this entire chapter had to compress down to a single sentence, this is it — nearly every other question in this chapter is really an elaboration on one half or the other of this exact distinction.

9. How does MongoDB route a query in a sharded cluster to the shards that actually hold the relevant data?​

📖 Introduction​

This question covers the piece of infrastructure that makes sharding transparent to the application making the query.

🧭 How Routing Works​

Applications connect to a routing process, rather than directly to any individual shard, which knows how data is distributed across the cluster based on the shard key, from earlier in this chapter, and forwards each query only to the specific shard, or shards, that could actually hold matching data, then combines the results before returning them to the application.

🎯 Why This Matters for Query Design​

A query that includes the shard key in its filter can be routed directly to the one specific shard that holds the relevant data — a targeted, efficient operation. A query that doesn't include the shard key has to be broadcast to every shard in the cluster, since the router has no way to narrow down which shard actually holds the matching data, which is significantly less efficient at scale.

💎 Good to Know: This Is a Direct, Practical Reason the Shard Key Should Reflect Your Actual, Common Query Patterns​

This connects directly back to the shard-key-selection questions earlier in this chapter — a shard key chosen purely for even distribution but ignored by your application's actual common queries forces most operations into the less efficient, broadcast-to-every-shard path described here.

10. How would you design a highly available MongoDB deployment for an application with a global user base?​

📖 Introduction​

This applied, closing-style question pulls together nearly every concept in this chapter into one realistic deployment design.

🔧 Design Approach​

Use replica sets, from earlier in this chapter, with members deliberately distributed across multiple geographic regions or availability zones, so that a regional outage doesn't take down the entire deployment. Use read preferences, from earlier in this chapter, to let users read from a replica set member that's geographically closer to them, reducing latency, while being deliberate about the resulting consistency trade-off for use cases that genuinely need the absolute latest data. If the dataset or write volume genuinely requires it, shard the data, from earlier in this chapter, with a shard key chosen to reflect real, common query and write patterns, potentially aligned with how the user base itself is geographically distributed.

💎 Good to Know: This Design Combines Every Major Concept From This Chapter Into One Coherent Whole​

Geographic replica distribution for availability, read preferences for latency, and sharding for scale, when genuinely needed, are exactly the three tools this chapter has built up — the actual skill this closing-style question tests is combining them thoughtfully for a specific, real scenario rather than reciting each one in isolation.

11. When should sharding genuinely be avoided, even if a collection is fairly large?​

📖 Introduction​

This closes the chapter with a deliberate caution against reaching for sharding by default.

⚠️ When to Avoid It​

When the collection, while large, still comfortably fits and performs well on a single, appropriately resourced server — sharding introduces real operational complexity, from the chunk-balancing and query-routing questions earlier in this chapter, that isn't worth taking on until it's genuinely necessary. When there's no clear, well-distributing shard key available for the data, from earlier in this chapter — sharding with a poor shard key can leave you with all the operational complexity and none of the actual distributed benefit.

🎯 A Better First Step in Many Cases​

Vertical scaling, a more capable single server, or the read-scaling benefits of replication alone, from earlier in this chapter, often address a genuine performance problem without needing sharding's added complexity at all — the same "don't reach for the most powerful tool before confirming it's genuinely needed" reasoning that recurs throughout this repo's Scalability guide.

💎 Good to Know: Sharding Is a Powerful Tool With a Real Ongoing Operational Cost, Not a Default "Bigger Is Better" Setting​

This closing caution mirrors the Scalability guide's broader theme directly — reach for the more powerful, more complex tool once the simpler ones are genuinely exhausted, not as a first, default instinct just because a collection happens to be large.
