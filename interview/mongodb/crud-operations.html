CRUD Operations

1. What do insertOne() and insertMany() each do, and when would you reach for one over the other?​

📖 Introduction​

These are the two most basic ways to get data into MongoDB, and the difference is exactly what the names suggest — the interesting part is when each is actually the right call.

➕ insertOne()​

Inserts a single document into a collection, returning the inserted document's _id.

db.users.insertOne({ name: "Priya", email: "priya@example.com" });

➕ insertMany()​

Inserts an array of multiple documents in a single call.

db.users.insertMany([
  { name: "Asha", email: "asha@example.com" },
  { name: "Ravi", email: "ravi@example.com" }
]);

🎯 When to Use Each​

insertOne() fits a single, discrete write, like a new user signing up. insertMany() fits genuinely batch scenarios, like importing a dataset or seeding data — it's meaningfully more efficient than calling insertOne() in a loop, since it sends the documents to the server in one round trip rather than many.

💎 Good to Know: insertMany() Isn't Automatically Atomic Across All Documents by Default​

By default, if one document in the batch fails to insert, insertMany() still attempts the rest and reports which ones succeeded and which failed — it doesn't automatically roll back the entire batch, which is a genuinely important detail worth confirming against your specific driver's exact default behavior before relying on it.

2. What's the difference between find() and findOne()?​

📖 Introduction​

Both retrieve documents matching a filter — the difference is in how many, and in what shape, they hand back.

🔍 find()​

Returns a cursor over every document matching the given filter — potentially many documents, which you then iterate over or convert to an array.

db.users.find({ role: "admin" });

🔍 findOne()​

Returns a single document — the first one matching the filter — or null if nothing matches, rather than a cursor.

db.users.findOne({ email: "priya@example.com" });

🎯 When to Use Each​

findOne() fits situations where you expect, or only care about, a single result — looking up a user by a unique field like email. find() fits situations where you genuinely expect, and want, a collection of matching results, like listing all posts by a given author.

💎 Good to Know: findOne() Doesn't Guarantee "the Only Match" — Just "the First One Found"​

If multiple documents match the filter passed to findOne(), it simply returns the first one it encounters, without any implied guarantee about which one that is unless the query also specifies a sort — worth being deliberate about a filter's actual uniqueness before relying on findOne().

3. What's the difference between updateOne(), updateMany(), and replaceOne()?​

📖 Introduction​

These three cover updating existing documents, but they differ in both how many documents they touch and how much of a document they actually change.

✏️ updateOne()​

Updates the first document matching a filter, applying specific changes via update operators, from later in this chapter, while leaving the rest of the document untouched.

✏️ updateMany()​

Applies the same kind of update to every document matching the filter, not just the first one.

🔄 replaceOne()​

Replaces the entire matched document with a completely new one, rather than applying targeted changes — any field not present in the replacement document is simply gone from the result.

💎 Good to Know: replaceOne() Is Genuinely Different From updateOne(), Not Just a Stricter Version of It​

updateOne() with update operators modifies specific fields while preserving everything else; replaceOne() throws away the entire existing document structure in favor of the new one you provide — accidentally reaching for replaceOne() when you meant a targeted update is a real, common way to unintentionally lose data, covered further later in this chapter.

4. What is an upsert operation, and what's a realistic use case for one?​

📖 Introduction​

"Upsert" is a portmanteau of "update" and "insert," and it does exactly what that name implies.

🔀 What It Is​

An update operation with the upsert option set to true — if a document matching the filter exists, it's updated normally; if no document matches, a new document is inserted instead, using the filter and update criteria to construct it.

db.counters.updateOne(
  { name: "pageViews" },
  { $inc: { count: 1 } },
  { upsert: true }
);

🎯 A Realistic Use Case​

Incrementing a counter that might not exist yet, like the page-view counter above — without upsert, you'd need a separate check for whether the counter document already exists before deciding whether to insert or update it, which is both extra code and a potential race condition between the check and the actual write.

💎 Good to Know: Upsert Removes an Explicit "Check, Then Decide" Step and Its Race Condition​

Handling the insert-or-update decision atomically, in a single operation, is exactly why upsert exists — doing the equivalent as two separate steps in application code introduces a window where two concurrent requests could both decide to insert, creating an unwanted duplicate.

5. What's the difference between updateOne() and findOneAndUpdate()?​

📖 Introduction​

Both update a single matching document — the difference is in what each one actually gives you back afterward.

✏️ updateOne()​

Returns metadata about the operation — how many documents matched and how many were actually modified — but not the document's content itself.

🔍 findOneAndUpdate()​

Updates a single matching document and also returns the actual document — either its state before the update or after it, depending on the option you specify — in the same single operation.

🎯 When findOneAndUpdate() Is the Better Choice​

Whenever you need the updated, or the previous, document's actual content right after the update, findOneAndUpdate() gets it in one round trip, rather than needing a separate find call after updateOne(), which also reopens the same kind of race-condition risk the previous question's upsert example was designed to avoid.

💎 Good to Know: findOneAndUpdate() Is the Right Tool Whenever "Update and Then Immediately Use the Result" Is the Actual Goal​

Any time application logic needs to act on the document's value immediately after updating it, from the previous question's counter example to returning a freshly updated record from an API endpoint, findOneAndUpdate() avoids both an extra round trip and a subtle race condition.

6. How do update operators like $set, $unset, $inc, and $push work, and why use them instead of replacing a whole document?​

📖 Introduction​

Update operators are what let updateOne()/updateMany() make targeted changes without touching the rest of a document, directly connecting back to the replaceOne() distinction earlier in this chapter.

🔧 What Each One Does​

$set sets the value of a specific field, creating it if it doesn't already exist. $unset removes a specific field entirely. $inc increments, or decrements with a negative value, a numeric field by a given amount. $push appends a new element onto an array field.

db.users.updateOne(
  { _id: userId },
  { $set: { status: "active" }, $inc: { loginCount: 1 }, $push: { tags: "verified" } }
);

🎯 Why Use Them Instead of Replacing the Whole Document​

Update operators change only the fields you actually specify, leaving everything else in the document exactly as it was — reading the entire document, changing one field in application code, and writing the whole thing back with replaceOne() is both more work and genuinely riskier, since it can silently overwrite a concurrent change to a different field made by another operation in between your read and your write.

💎 Good to Know: Targeted Update Operators Are the Safer Default for Concurrent Writes​

This directly connects to the earlier concurrent-write concern flagged in the upsert question — using $set and similar targeted operators, rather than a read-modify-write-back pattern, is one of the most practical ways to avoid the kind of lost-update race condition covered later in this chapter.

7. How do projection, sorting, skipping, and limiting work together in a single query?​

📖 Introduction​

These four are commonly chained together on the same query, each shaping a different aspect of the final result.

🧩 What Each One Does​

Projection selects which fields of a matching document are actually returned, rather than the whole document. Sorting orders the results according to one or more fields. Skipping omits a given number of results from the beginning of the result set. Limiting caps how many results are returned at most.

db.posts
  .find({ published: true })
  .project({ title: 1, author: 1 })
  .sort({ createdAt: -1 })
  .skip(20)
  .limit(10);

🎯 A Realistic Combination​

This exact combination is a classic paginated listing — the tenth page of ten published posts each time, sorted newest-first, returning only the fields the listing view actually needs rather than the full document.

💎 Good to Know: skip() Has a Real Performance Cost at Scale, Covered Later in This Guide​

Combining skip() with limit() for pagination, exactly as shown here, works correctly but has a genuine performance downside for deep pagination on large collections — covered in more depth in the Query Operators chapter of this guide.

8. What are bulk write operations, and when do they meaningfully outperform issuing many individual operations?​

📖 Introduction​

Bulk operations exist for the same underlying reason insertMany() does — reducing round trips between the application and the database.

📦 What They Are​

A single call that bundles multiple write operations, inserts, updates, deletes, or a mix of all three, into one request sent to the database, rather than sending each one as its own separate, individual call.

db.users.bulkWrite([
  { insertOne: { document: { name: "Neha" } } },
  { updateOne: { filter: { name: "Ravi" }, update: { $set: { status: "active" } } } },
  { deleteOne: { filter: { name: "Old User" } } }
]);

🎯 When They Meaningfully Outperform Individual Calls​

Whenever you're already performing many separate write operations in a loop — each individual call carries its own network round-trip overhead, and bundling them into one bulk call meaningfully reduces that overhead, especially noticeable as the number of operations grows into the hundreds or thousands.

💎 Good to Know: Bulk Operations Are the Direct MongoDB Answer to the Batching Principle Covered Throughout This Repo​

This is the same underlying batching-over-many-individual-calls idea covered generally in the API & Backend Scenarios chapter of the Production Scenario Questions guide — bulk writes are simply MongoDB's specific mechanism for applying that idea to database operations.

9. What's the difference between deleting a document and replacing it with an empty one?​

📖 Introduction​

These sound similar but result in genuinely different states, worth being precise about the distinction.

🗑️ Deleting​

deleteOne() or deleteMany() removes the matching document, or documents, from the collection entirely — the document, and its _id, no longer exist at all.

🔄 Replacing With an Empty Document​

replaceOne(), from earlier in this chapter, with an empty or near-empty replacement document, keeps a document in existence at the same _id, but strips it down to essentially nothing — the document still exists, it's just now empty.

🎯 Why This Distinction Matters​

Anything that references the document by its _id, from the Relationships chapter of this guide, still finds a document there after a replace, just an empty one — but finds nothing at all after a genuine delete, which can produce very different, and differently confusing, downstream behavior depending on which one actually happened.

💎 Good to Know: This Is a Deliberate API Distinction, Not an Accidental Overlap​

MongoDB gives you deleteOne() and replaceOne() as genuinely separate operations specifically because "this record no longer exists" and "this record exists but now has no meaningful content" are two different states an application might actually need to distinguish between.

10. How would you prevent a race condition when two concurrent requests try to update the same document?​

📖 Introduction​

This question ties together several tools introduced earlier in this chapter into a direct answer for a genuinely common concurrency problem.

⚠️ The Risk​

Two concurrent requests each read a document, each independently decide on a change based on what they read, and then each write their own version back — the second write can silently overwrite the first one's change, a classic lost-update problem, closely related to the two-services-overwriting-updates scenario from the Production Scenario Questions guide's Database Scenarios chapter.

🔧 How to Prevent It​

Use targeted update operators, $inc or $set, from earlier in this chapter, instead of a read-modify-write-back pattern, since operators like $inc are applied atomically by MongoDB itself against whatever the document's current value actually is at the moment of the write, not against a possibly-stale value read earlier. For more complex, conditional updates, include the expected current value directly in the update's filter, so the update only succeeds if the document still matches the state it was expected to be in, and use findOneAndUpdate(), from earlier in this chapter, to detect and react to the case where it doesn't.

💎 Good to Know: Atomic, Single-Document Operations Are MongoDB's Built-in Answer to Many Concurrency Problems​

A single document's write in MongoDB is always atomic — leaning on that guarantee with targeted operators, rather than a multi-step read-then-write pattern in application code, resolves a large share of concurrency concerns without needing a full multi-document transaction, covered later in this guide, at all.

11. What are common mistakes developers make while writing update operations, especially around accidentally replacing an entire document?​

📖 Introduction​

Most of these mistakes trace directly back to the updateOne()-versus-replaceOne() distinction from earlier in this chapter.

❌ Passing a Plain Object Without an Operator to updateOne()​

Some drivers and versions treat an update argument with no operators like $set as an implicit full replacement — meaning a call intended as a small, targeted update can accidentally behave like replaceOne(), wiping out every field not explicitly included.

❌ Reaching for replaceOne() Out of Habit for What Should Be a Targeted Update​

Using replaceOne() for a routine field update, then being surprised that fields outside the replacement document quietly disappeared.

❌ Forgetting upsert: true and Assuming an Update Will Create a Missing Document​

Expecting an update to a non-existent document to fail loudly, when by default it simply matches nothing and does nothing at all, silently, unless upsert, from earlier in this chapter, was explicitly set.

❌ Using updateMany() When Only One Document Was Actually Intended to Change​

A filter that was expected to match only one document, but actually matches several, silently applying the same change far more broadly than intended.

💎 Good to Know: Being Explicit About Intent — Targeted Update vs. Full Replacement — Prevents Nearly All of These​

Nearly every mistake on this list comes down to an update operation's actual behavior not matching what the developer assumed it would do — being deliberate about which specific method and operators you're reaching for, rather than treating them as interchangeable, is what prevents this entire category of bug.

12. How would you design CRUD operations to stay performant as a collection grows into the millions of documents?​

📖 Introduction​

This closing question pulls together several threads from this chapter and previews concepts covered in more depth later in this guide.

🎯 Design Considerations​

Ensure every common query filter is backed by an appropriate index, covered in depth in the Indexing chapter of this guide, since a query without one degrades from a fast, targeted lookup into a full collection scan as the collection grows. Use projection, from earlier in this chapter, to avoid pulling entire large documents back over the network when only a few fields are actually needed. Use bulk operations, from earlier in this chapter, for any batch write workload, rather than looping over many individual calls. Prefer cursor-based pagination over skip()/limit() for deep pagination, covered in the Query Operators and Performance Optimization chapters of this guide, since skip()'s cost grows with how deep into the results you're paging.

💎 Good to Know: None of These Individually Sophisticated — Together They're What Separates a Toy Schema From a Production One​

Every technique here has already been introduced earlier in this chapter or is covered elsewhere in this guide — the actual skill being tested by this closing question is recognizing that they need to be applied together, deliberately, rather than only reached for reactively once a collection is already struggling under real production scale.
