Indexing

1. What is an index in MongoDB, and how does it actually speed up a query?​

📖 Introduction​

Indexes have been referenced constantly throughout this guide so far — this chapter is where they finally get full, dedicated coverage.

🧩 What It Is​

A separate, ordered data structure that stores the values of a specific field, or fields, alongside a pointer back to the full document each value belongs to — conceptually similar to a book's index, which lets you jump straight to a page rather than reading the entire book to find a topic.

⚡ How It Speeds Up a Query​

Without an index, MongoDB has to check every single document in a collection to find matches for a query — a collection scan, from the next question. With an appropriate index, MongoDB can look up the relevant values directly in that ordered structure, then jump straight to only the matching documents, without needing to examine every other document in the collection at all.

💎 Good to Know: An Index Speeds Up Reads at a Real Cost to Writes​

This trade-off, first introduced in the Production Scenario Questions guide's Database Scenarios chapter, is a running theme throughout this entire chapter — every index that helps a read has to be maintained on every write to the collection, which is exactly why indexing isn't a costless "add more, get more speed" decision.

2. What's the difference between a collection scan and an index scan?​

📖 Introduction​

These are the two fundamentally different ways MongoDB can actually execute a query.

🔍 Collection Scan​

MongoDB examines every single document in the collection, checking each one against the query's filter — the query's execution time grows roughly in proportion to the total size of the collection, regardless of how few documents actually match.

⚡ Index Scan​

MongoDB uses an index, from the previous question, to directly locate matching documents, without needing to examine every document in the collection — execution time depends much more on how many documents actually match, and how efficiently the index itself can be traversed, than on the collection's total size.

💎 Good to Know: A Query That Works Fine on a Small Collection Can Become a Real Problem Purely From Growth​

A collection scan on a small, mostly-development-sized collection is fast enough to go unnoticed — the exact same query, unchanged, becomes measurably slower purely as the collection grows, which is exactly why confirming a query actually uses an index, using explain() from later in this chapter, matters well before a collection reaches real production scale.

3. What is a compound index, and why does the order of fields within it matter so much?​

📖 Introduction​

Field order in a compound index isn't a stylistic choice — it fundamentally determines what the index can actually be used for.

🔗 What It Is​

An index built across more than one field at once, rather than a single field on its own.

db.orders.createIndex({ userId: 1, createdAt: -1 });

🎯 Why Field Order Matters​

A compound index is structured like a phone book sorted by last name, then first name — you can efficiently look up by last name alone, or by last name and first name together, but you can't efficiently look up by first name alone using that same structure. Similarly, this index can efficiently serve queries filtering on userId alone, or on userId and createdAt together, but generally can't efficiently serve a query that filters only on createdAt, since that field isn't the leading field of the index.

💎 Good to Know: This Directly Explains a Common "Why Isn't My Index Being Used" Confusion​

This is exactly the mechanism behind the earlier Query Operators chapter's discussion of a query failing to use an existing index — an index technically exists, it's just not usable for a query that doesn't include that index's specific leading field.

4. What is a multikey index, and how does it let MongoDB index a field that holds an array?​

📖 Introduction​

Arrays are common in MongoDB documents, from the Data Modeling chapter of this guide — indexing them needs a slightly different approach than indexing a plain scalar field.

🔢 What It Is​

An index MongoDB automatically creates when the indexed field holds an array — rather than indexing the array as a single value, MongoDB creates a separate index entry for each individual element within the array.

{ "_id": 1, "tags": ["mongodb", "database", "nosql"] }

Indexing tags here creates three separate index entries, one for each tag, any of which can be used to find this document.

🎯 Why This Matters​

This is what lets a query like { tags: "nosql" } efficiently find documents where the array contains that specific value, without needing to individually scan and check every document's entire array contents.

💎 Good to Know: MongoDB Creates a Multikey Index Automatically — It's Not a Separate Index Type You Explicitly Choose​

You don't declare an index as "multikey" yourself — MongoDB automatically indexes it that way the moment it detects the field actually holds an array in at least one document, which is worth knowing since it affects how that index behaves without requiring any special syntax on your part.

5. What is a text index, and what kind of query does it actually enable?​

📖 Introduction​

A text index solves a genuinely different problem than the exact-match and range queries covered so far in this guide.

🔤 What It Is​

A special index type built specifically for searching string content — rather than matching an exact value, it indexes the individual words within a text field, enabling actual text search.

db.articles.createIndex({ title: "text", body: "text" });
db.articles.find({ $text: { $search: "mongodb performance" } });

🎯 What It Enables​

Finding documents that contain any of the given search words, generally with some relevance ranking, rather than requiring an exact string match — genuinely different from a normal equality or range query on a string field.

💎 Good to Know: A Text Index Is a Basic Search Tool, Not a Full Search Engine Replacement​

For simple, built-in text search needs, MongoDB's text index is genuinely useful — but for more sophisticated search requirements, relevance tuning, typo tolerance, faceted search, a dedicated search engine is typically the better fit, with MongoDB's text index serving as the reasonable, lower-effort default until that becomes genuinely necessary.

6. What is a TTL index, and what's a realistic use case for one?​

📖 Introduction​

TTL stands for "time to live," and this index type is specifically about automatic, scheduled document expiration.

⏰ What It Is​

An index on a date field that causes MongoDB to automatically delete documents once a specified amount of time has passed since the value in that field.

db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 });

🎯 A Realistic Use Case​

Session documents, from the Web Security guide's Session & Token Security chapter, that should automatically expire and be cleaned up after a period of inactivity or a fixed session length, without needing a separate, manually scheduled cleanup job to periodically delete old ones.

💎 Good to Know: TTL Deletion Isn't Instant the Moment a Document Expires​

MongoDB runs a background process that periodically checks for and removes expired documents, rather than deleting them at the exact instant they technically expire — worth knowing that there's a small, generally acceptable delay between a document becoming eligible for deletion and it actually being removed.

7. What's the difference between a sparse index and a partial index?​

📖 Introduction​

Both exist to avoid indexing every single document in a collection — they just decide which documents to skip in different ways.

🕳️ Sparse Index​

Only includes documents where the indexed field actually exists — documents missing that field entirely are simply excluded from the index.

🎯 Partial Index​

Only includes documents that match an explicitly specified filter condition, which can be far more flexible than simply "field exists or doesn't."

db.orders.createIndex(
  { total: 1 },
  { partialFilterExpression: { status: "completed" } }
);

🆚 Why Partial Is Generally More Flexible​

A sparse index's only real criterion is field presence; a partial index can express any filter condition — every sparse index's behavior can be reproduced with an equivalent partial index, but not the other way around, which is why partial indexes are generally the more modern, more flexible recommendation.

💎 Good to Know: Both Exist to Keep an Index Smaller and More Efficient by Deliberately Excluding Irrelevant Documents​

The shared underlying goal here is avoiding the size and maintenance cost of indexing documents that will genuinely never be relevant to the queries that index is meant to serve — a smaller, more targeted index is both faster to use and cheaper to maintain on writes.

8. Why can having too many indexes on a collection actually hurt performance?​

📖 Introduction​

This is the direct, concrete consequence of the read/write trade-off flagged in the very first question of this chapter.

⚠️ Why It Hurts​

Every index on a collection has to be updated on every single write to that collection, from the first question of this chapter — a collection with many indexes pays that update cost repeatedly, once per index, on every insert, update, and delete, which can meaningfully slow down write-heavy workloads. Indexes also consume real storage and memory, and a large number of indexes competing for available memory can push frequently used indexes out of memory, forcing slower disk access even for queries that should otherwise be fast.

🎯 The Practical Implication​

Indexing isn't a "the more, the better" decision — every index needs to earn its place by genuinely serving a real, frequent query pattern, weighed against its ongoing write and storage cost.

💎 Good to Know: An Unused Index Is Pure Cost With No Offsetting Benefit​

An index that isn't actually used by any real query is the worst version of this trade-off — all of the write and storage cost, from earlier in this chapter, with none of the read benefit that would normally justify it, which is exactly why identifying and removing unused indexes, covered later in this chapter, matters.

9. How do you use explain() to understand whether a query is actually using the index you expect?​

📖 Introduction​

explain() has been referenced repeatedly throughout this entire guide — this is where it's actually covered directly.

🔍 What It Does​

Returns a detailed breakdown of exactly how MongoDB actually executed a given query — which stage type it used, COLLSCAN for a full collection scan or IXSCAN for an index scan, from earlier in this chapter, which specific index was used if any, and how many documents were actually examined versus how many were ultimately returned.

db.orders.find({ userId: "user1" }).explain("executionStats");

🎯 What to Actually Look For​

Whether the plan shows IXSCAN rather than COLLSCAN, and whether the number of documents examined is reasonably close to the number of documents actually returned — a large gap between the two suggests the index being used, if any, isn't narrowing things down as efficiently as it could.

💎 Good to Know: explain() Replaces Assumption With Actual Evidence​

Assuming a query is using an index just because one technically exists on the field involved is one of the most common indexing mistakes covered throughout this guide — explain() is the direct, reliable way to confirm what's actually happening rather than trusting an assumption.

10. How does MongoDB's query planner choose which index to use when multiple indexes could apply?​

📖 Introduction​

A collection can have several indexes that could each theoretically serve a given query — this question is about how MongoDB picks one.

🧠 How It Decides​

MongoDB's query planner evaluates candidate query plans, ones using different available indexes, on an actual trial basis, and picks the plan that performs best empirically — it then generally caches that decision so future, similar queries can skip straight to the winning plan without re-evaluating every candidate each time.

🔄 Why the Cached Choice Can Change​

If the underlying data or its distribution changes meaningfully over time, or if the collection's indexes themselves change, MongoDB will re-evaluate and can select a different plan than it previously cached — worth being aware of if a query's performance ever changes despite no application-level code change.

💎 Good to Know: You Can Verify Which Plan Actually Won Using explain()​

explain(), from the previous question, shows not just whether an index was used, but specifically which one was chosen when multiple were genuinely viable — useful for confirming the planner actually picked the index you intended, rather than a different, technically-also-valid one.

11. How would you design an indexing strategy for a collection that's both read-heavy and write-heavy?​

📖 Introduction​

This applied question forces the read/write trade-off from the first question of this chapter into an actual, concrete design decision.

🔧 Design Approach​

Identify the specific, actually-frequent query patterns first, rather than indexing defensively for every field that theoretically might be queried someday — every index added has a real write cost, from earlier in this chapter, so each one needs to justify its place against genuine, observed usage. Favor a smaller number of well-chosen compound indexes, from earlier in this chapter, that each serve several related query patterns, over many narrow, single-field indexes that collectively add up to more total write overhead. Periodically re-evaluate which indexes are actually still being used, from the next question, since query patterns shift as an application evolves.

💎 Good to Know: There's No Universal Answer — Only a Deliberate Trade-off Specific to the Actual Workload​

A collection that's overwhelmingly read-heavy can reasonably afford more indexes than one that's genuinely write-heavy — the right answer here depends entirely on the collection's actual, measured read-to-write ratio, not a fixed, one-size-fits-all rule.

12. How would you identify and remove unused or redundant indexes in a production database?​

📖 Introduction​

This closing question addresses the "pure cost, no benefit" problem flagged earlier in this chapter directly.

🔍 Identifying Unused Indexes​

Use MongoDB's index usage statistics, which track how many times each index has actually been used to serve a query since the server last started, to identify indexes that are rarely or never actually hit by real traffic.

🔍 Identifying Redundant Indexes​

Look for indexes that are effectively subsets of a broader compound index already covering the same, or a superset of, fields, from earlier in this chapter's compound-index discussion — a standalone index on userId alone is often already redundant if a compound index starting with userId also exists.

🔧 Removing Them Safely​

Confirm an index genuinely isn't in use across a representative period of real traffic, not just a quiet moment, before dropping it — and monitor query performance immediately after removal to confirm nothing regresses unexpectedly.

💎 Good to Know: This Is the Practical, Ongoing Maintenance Half of Indexing, Not a One-Time Setup Task​

Just as with schema validation, from earlier in this guide, indexes need periodic review as an application's actual query patterns evolve — an indexing strategy set up once early on and never revisited tends to accumulate exactly this kind of unused, pure-cost cruft over time.
